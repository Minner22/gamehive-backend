# Ekspert: `auth/`

Jak pracować: każdą odpowiedź opieraj na kodzie (podawaj `plik:linia`), a nie na tym skillu — skill mówi, **gdzie** patrzeć i **czego nie zepsuć**. Reguły przekrojowe (GH-63, audyt, cache) są też w CLAUDE.md, w sekcji "Security & JWT pipeline".

## Mapa kodu
| Klasa | Odpowiedzialność |
|---|---|
| `controller/AuthController` | jedyne wejście `/api/v1/auth/**`. **Część logiki tokenów żyje tutaj, nie w serwisie**: `/activate` i `/password-reset/confirm` walidują token wspólnym prywatnym `validateOneTimeToken` (podpis/typ/exp → blacklista JTI → epoka `iat < epoka` → `TOKEN_REVOKED`; komunikaty to stała etykieta + stały tekst, GH-145), a po sukcesie same blacklistują token; `generateTokens` buduje cookie refresh |
| `service/AuthServiceImpl` | `register` (+`UserRegisteredEvent`), `login` (stały czas: dummy bcrypt), `activateUser`, `requestPasswordReset` (milczy przy nieznanym e-mailu), `confirmPasswordReset` (+`UserCredentialsChangedEvent` + audyt `PASSWORD_CHANGE`), `resendActivationEmail` (tylko nieaktywni) |
| `jwt/service/JwtServiceImpl` | Nimbus JOSE, HS256, osobny sekret per typ; `validateToken` = algorytm → podpis → `exp` → claim `type` → (REFRESH) niepusty JTI — **bez Redisa** (GH-146). `rotateRefreshToken(token, credentialsLoader)` = `validateToken` → loader(email ze zweryfikowanego tokena) → nowa para budowana (`issue`, bez zapisu) → `RedisRefreshTokenStore.rotate` → `CONSUMED` zwraca parę / `UNKNOWN` → `JWT_INVALID_JTI` / `REUSED` → WARN + `RefreshTokenReuseDetectedEvent` + `REFRESH_TOKEN_REUSED`. `generateToken(REFRESH)` zapisuje JTI w Redis sam |
| `jwt/service/RedisRefreshTokenStore` | `refresh_token:{jti}` → email (TTL = ważność), ZSET `user_refresh_tokens:{email}` (score = czas wydania); limit `maxActiveTokensPerUser` (5) usuwa najstarszy. `rotate` (GH-146) = jeden skrypt Lua: `DEL` starego → `ZREM` + znacznik `refresh_rotated:{jti}` (email, TTL = pozostała ważność) **+ zapis następcy** (`SET` + `ZADD`) → `CONSUMED`; bez tokena znacznik rozstrzyga `REUSED` / `UNKNOWN` (enum `auth/jwt/RefreshTokenConsumeResult`). `revokeAllByUserEmail` też jednym skryptem (`ZRANGE` + `DEL`) |
| `jwt/service/TokenBlacklistServiceImpl` | `blacklist:{jti}` z TTL = pozostała ważność; `isBlacklisted` **fail-open** (filtr, `/activate`), `isBlacklistedStrict` **fail-closed** → `REDIS_UNAVAILABLE` (`/password-reset/confirm`, GH-168); zapis przy awarii Redis jest połykany (log ERROR) |
| `jwt/service/RedisSessionEpochStore` | `token_invalid_after:{email}` (ms, TTL = ważność ACCESS) oraz `activation_invalid_after:{email}` i `password_reset_invalid_after:{email}` (GH-145) — obie **ucięte do pełnych sekund**, TTL = ważność danego typu tokena; odczyt **fail-open** (null) — **poza epoką resetu, która jest strict** (`getEpochStrict`, jedyny konsument to `confirm`, GH-168) — zapis rzuca `REDIS_UNAVAILABLE` |
| `jwt/service/UserAuthStateProvider` | `@Cacheable("userAuthState")`: `{enabled, authorities z DB, invalidAfter}` |
| `config/JwtAuthFilter` | Bearer → validate ACCESS → blacklist (fallthrough do entry pointu) → stan użytkownika: disabled = `ACCOUNT_DISABLED`, `iat < epoka` = `TOKEN_REVOKED` (oba pisze sam jako `ApiError`) → principal = **email jako String**. `shouldNotFilter`: login/register/refresh. Wyjątki: `ApplicationException` (zły token) → DEBUG, inny `RuntimeException` → **ERROR ze stack trace'em** — w obu przypadkach łańcuch idzie dalej i odpowiada entry point (GH-165) |
| `config/SecurityConfig` | stateless, CSRF off, `permitAll`: h2-console, `/api/v1/auth/**`, swagger; entry point = 401 `ACCESS_DENIED`; `DelegatingPasswordEncoder` (`{bcrypt}`); `FilterRegistrationBean<JwtAuthFilter>` z `setEnabled(false)` — `JwtAuthFilter` działa **tylko** w łańcuchu Security (GH-163) |
| `event/AuthEmailEventListener` | `@Async("authEmailExecutor")` + AFTER_COMMIT; generuje token i wysyła mail; przy resend aktywacji i przy **każdym** żądaniu resetu hasła **najpierw** epoka (fail-closed: Redis padł = brak maila, endpoint i tak 200) |
| `jwt/config/*Properties` | `jwt.{access,refresh,activation,passwordreset}.{secret,validityInSeconds}`; w `test` ACCESS i ACTIVATION żyją **2 s** |

## Przepływy, które trzeba znać
- **Uprawnienia pochodzą z bazy, nie z tokena.** Claim `roles` w ACCESS jest wymagany przy generowaniu, ale filtr bierze `authorities` z `UserAuthStateProvider`. Zmiana ról działa więc od razu po eviction cache — bez nowego tokena.
- **Unieważnianie (GH-63)**: zdarzenia z `user/event` → `UserSecurityEventListener` (AFTER_COMMIT) → `revoke` = usunięcie refreshów + epoka sesji + eviction cache. Reaktywacja i zmiana ról robią tylko eviction (bez czyszczenia epoki).
- **Logout** (GH-148): `validateToken` → cookie wyczyszczone na `HttpServletResponse` (przetrwa odpowiedź błędu, bo `DispatcherServlet` robi `resetBuffer()`, nie `reset()`) → `blacklistTokenStrict` ACCESS i `revokeUsersTokens` (wszystkie refreshe użytkownika, czyli wylogowanie ze wszystkich urządzeń) — **oba kroki próbowane niezależnie**, dowolna awaria → 503 `REDIS_UNAVAILABLE` (z wyczyszczonym cookie), inaczej 200. Nieważny token → 401 bez ruszania cookie (świadomie: najpierw walidacja). Przy timeoucie wynik zapisu jest nieznany — na `dev` blacklista „z 503” wykonała się po odwieszeniu Redisa, a rewokacja (wymaga najpierw `ZRANGE`) nie; ponowny logout jest bezpieczny (idempotentny). Front ignoruje błąd logoutu i i tak czyści sesję lokalnie (`AuthContext.logout`).
- **Refresh** (GH-146): cookie `refreshToken` (path `/api/v1/auth/refresh`, HttpOnly, Secure, SameSite=Strict, 7 dni) → `rotateRefreshToken` (walidacja → lookup użytkownika → nowa para → atomowa rotacja; stary refresh przestaje działać). Ponowne użycie zrotowanego tokena → 401 `REFRESH_TOKEN_REUSED` + wylogowanie ze wszystkich urządzeń (`RefreshTokenReuseDetectedEvent` → `UserSecurityEventListener.revoke()`, to samo co force-logout). Wypchnięty limitem / po logoucie → zwykłe `JWT_INVALID_JTI`. Bez okna łaski — równoległe odświeżenia szereguje front (frontend#80). Limit 5 liczy teraz urządzenia, nie odświeżenia. Szczegóły i przyjęte ryzyko (utracona odpowiedź albo timeout Redisa = globalne wylogowanie przy ponownej próbie, potwierdzone na `dev` 2026-11-24) w CLAUDE.md.
- `AppUserDetailsService` + bean `authenticationProvider` istnieją, ale `login` **nie** używa `AuthenticationManager` — weryfikuje hasło sam (`HashedPassword.matches`).

## Niezmienniki — nie psuć
- `login`: nieznany e-mail i złe hasło = ten sam `INVALID_CREDENTIALS`; hasło sprawdzane **zawsze i jako pierwsze**; `USER_NOT_ACTIVATED` dopiero po poprawnym haśle.
- Porównania epok są **ostre** (`<`); epoki aktywacji i resetu hasła ucięte do sekund (inaczej świeży token wystawiony zaraz po epoce byłby odrzucony — patrz pamięć `project_resend_activation_design`). Pinuje to `AuthControllerTest.passwordReset_linkIssuedRightAfterEpoch_stillValid` i test resendu aktywacji; zamiana `<` na `<=` czerwieni oba.
- Epoka resetu hasła jest ustawiana przy żądaniu **i** po udanym resecie (`UserSecurityEventListener.onUserCredentialsChanged`, przed `revoke`) — ta druga chroni przed linkami z tej samej sekundy co ostatnie żądanie. Deaktywacja, delete i force-logout jej **nie** ruszają (to nie zmiana hasła).
- Side effecty bezpieczeństwa są **AFTER_COMMIT**, więc metoda serwisu publikująca zdarzenie **musi** być `@Transactional` (inaczej zdarzenie nie dotrze). **Wyjątek: `RefreshTokenReuseDetectedEvent`** (GH-146) — `/refresh` nie ma transakcji DB, więc jego handler to zwykły synchroniczny `@EventListener`; „ujednolicenie” do `@TransactionalEventListener` wyłączyłoby wykrywanie kradzieży bez żadnego błędu (pinuje `UserSecurityEventListenerTest.onRefreshTokenReuseDetected_isPlainEventListener`).
- **Weryfikacja refresh tokena = `rotateRefreshToken`, nigdy `validateToken(REFRESH)` + osobne sprawdzenie w Redis.** Sprawdzenie, konsumpcja i zapis następcy to jeden skrypt Lua: rozdzielone sprawdzenie przepuściłoby dwa równoległe odświeżenia (TOCTOU), sprawdzenie istnienia przed skryptem odpowiadałoby `JWT_INVALID_JTI`, zanim ktokolwiek zajrzy do znacznika (dlatego `existsByJti` usunięto), a **zapis następcy osobnym krokiem po konsumpcji to luka z security review GH-146**: złodziej wysyła dwa równoległe `/refresh`, przegrany wykrywa reuse i rewokuje ZSET, zanim następca zwycięzcy do niego trafi — właściciel wylogowany, złodziej z sesją. Access token budowany przed skryptem (`iat` ≤ rotacja < epoka) też pada. `revokeAllByUserEmail` jest jednym skryptem z tego samego powodu (rewokacja równoległa z rotacją). Pinuje `security/RefreshTokenReuseRaceTest` (deterministyczny przeplot: zatrzymanie zaraz po `rotate` i przed nim).
- Nieuwierzytelniony = **401**, nigdy 403. Nowe publiczne endpointy muszą leżeć pod `/api/v1/auth/**`. Gdy mają działać bez nagłówka, a mogą dostać stary Bearer, rozważ dopisanie do `shouldNotFilter`.
- Fail-open (blacklist, epoka) vs fail-closed (resend aktywacji, zapis refreshu) to świadome decyzje — nie ujednolicaj ich bez rozmowy. Tabela per konsument (GH-168) jest w CLAUDE.md. **Operacja, która zmienia stan bezpieczeństwa i której zabezpieczenia żyją w Redisie, używa odczytów strict** (wzór: `confirm` → `isBlacklistedStrict` + strict epoka resetu, 503 przed zmianą hasła); filtr i `/activate` zostają fail-open.
- **Cache `userAuthState` trzyma epokę sesji** (`UserAuthStateProvider` czyta ją z Redisa), więc po zapisie epoki trzeba go wyczyścić **ponownie** — `revoke()` czyści przed krokami Redis (deaktywacja działa od razu przy padniętym Redis) i w `finally` po nich. Samo czyszczenie na początku otwiera okno: żądanie w trakcie rewokacji zapisuje starą epokę na 60 s (regresja wyłapana w security review GH-168, pinuje `UserSecurityEventListenerTest.staleAuthState*`).
- **Niedostępny Redis = `RedisConnectionFailureException | QueryTimeoutException`** (GH-165) — każdy `catch` obsługi awarii Redis łapie oba (multi-catch), nigdy całe `DataAccessException` (błąd programistyczny, np. `WRONGTYPE`, nie może po cichu wyłączyć blacklisty). Testy awarii parametryzuj `support/RedisUnavailability#failures`; przypadek negatywny z `RedisSystemException` pinuje zakres.
- **Filtr-`@Component` przeznaczony dla łańcucha Security wymaga `FilterRegistrationBean` z `setEnabled(false)`** (GH-163). Inaczej Boot zarejestruje go drugi raz jako filtr servletowy (`LOWEST_PRECEDENCE`, a dla `OncePerRequestFilter` wszystkie typy dispatchu) — poza łańcuchem, po autoryzacji. Pinuje `security/JwtAuthFilterRegistrationTest` (przez `ServletContextInitializerBeans`, tę samą kolekcję, z której rejestruje Boot); bez beana test widzi włączoną rejestrację.
- `CorrelationIdFilter` działa **przed** łańcuchem (GH-163), więc każda odpowiedź 401/403 z Security ma `X-Correlation-Id`, a logi filtra mają MDC (`CorrelationIdSecurityOrderTest`).

## Testy, które to pinują
`auth/controller/AuthControllerTest`, `auth/service/AuthServiceImplTest`, `AuthServiceRollbackTest` (rollback = brak maila), `auth/jwt/service/*Test` (`RedisSessionEpochStoreFailureTest` = fail-open), `auth/event/AuthEmailEventListenerTest`, a przekrojowo pakiet `security/`: `AccessTokenInvalidationTest`, `ForceLogoutTest`, `PasswordChangeInvalidatesSessionsTest`, `RefreshTokenRevocationTest`, `RefreshTokenRotationTest` (GH-146: rotacja, reuse → globalne wylogowanie mimo rozgrzanego cache, wypchnięcie limitem / logout bez wylogowania, 503), `RefreshTokenReuseRaceTest` (security review GH-146: żaden token z wyścigu dwóch `/refresh` nie przeżywa wykrycia reuse), `UserAuthStateCacheTest`, `SecurityIntegrationTest`. Skrypty Lua i ich atomowość: `RedisRefreshTokenStoreTest.rotate_*` / `revokeAll_*` (w tym dwa wątki × 30 iteracji). Testy generują tokeny wprost przez `jwtService.generateToken(...)` i robią `flushAll()` na embedded Redis w `@BeforeEach`.

## Obserwacje z analizy kodu (2026-11-21) — zgłoszone jako issues, nie naprawiaj samodzielnie
1. **[#149] Komunikaty błędów zawierają dane wejściowe** — `GlobalExceptionHandler.buildResponse` kopiuje `ex.getMessage()` do `ApiError`, więc klient dostaje np. `"Invalid credentials for: jo***@example.com"` albo `"Username already exists: <username>"`. To nie jest wyrocznia enumeracji (obie gałęzie loginu mają ten sam kształt, a echo dotyczy własnego wejścia wołającego), ale stoi w sprzeczności z regułą "static messages", którą przyjęto dla wyszukiwarki (GH-122).
2. ~~[#145] Blacklistowany token resetu hasła dostaje komunikat o tokenie aktywacyjnym~~ — **rozwiązane w GH-145** (wspólny helper z etykietą typu tokena).
3. ~~[#145] Starsze linki resetu hasła nie są unieważniane~~ — **rozwiązane w GH-145** (epoka `password_reset_invalid_after`, zob. mapa i niezmienniki; zweryfikowane na `dev` 2026-11-21).
4. ~~[#146] Brak rotacji refresh tokenów i wykrywania ich ponownego użycia~~ — **rozwiązane w GH-146** (zob. „Refresh” wyżej; zweryfikowane na `dev` 2026-11-24).
5. ~~[#148] Logout przy awarii Redis~~ — **rozwiązane w GH-148** (zob. „Logout” wyżej; zweryfikowane na `dev` 2026-11-23). `blacklistToken` (połykający) zostaje tylko po udanych operacjach jednorazowych (`/activate`, `confirm`); logout używa `blacklistTokenStrict`.
6. [#150] `RedisRefreshTokenStore` loguje **pełny e-mail** na poziomie ERROR; reszta modułu używa `obfuscated()`.
8. [#172] `/refresh` nie sprawdza `enabled` — wyłączone konto z ocalałym refresh tokenem (np. po best-effort rewokacji przy padniętym Redisie) mogłoby rotować w nieskończoność; access tokeny i tak odbija filtr (`ACCOUNT_DISABLED`). Obserwacja z security review GH-146, problem sprzed tej zmiany.
7. ~~[#165] Timeout Redis omija obsługę awarii~~ — **rozwiązane w GH-165** (multi-catch w 9 miejscach + `JwtAuthFilter` loguje awarie na ERROR; zweryfikowane na `dev` 2026-11-23: poprawny Bearer przy wstrzymanym Redis → 200, `/refresh` → 503). Historia dla kontekstu: `RedisSessionEpochStore`, `TokenBlacklistServiceImpl`, `RedisRefreshTokenStore` (i `SearchReindexService`) łapią tylko `RedisConnectionFailureException`, a zawieszony Redis (`docker pause`) daje po `spring.data.redis.timeout` (2 s) **`QueryTimeoutException`**. Fail-open odczytów (blacklista, epoki) i `REDIS_UNAVAILABLE` zapisów działają więc tylko przy odmowie połączenia; przy timeoucie leci nieprzetłumaczony wyjątek — w kontrolerze (`/activate`, `/password-reset/confirm`) 500, a w `JwtAuthFilter` połyka go `catch (Exception e)` z logiem tylko na DEBUG, więc żądanie z **poprawnym** tokenem dostaje 401 `ACCESS_DENIED` (de facto fail-closed i niewidoczne; potwierdzone na `dev` 2026-11-22, korekta w komentarzu #165). Testy awarii (`*FailureTest`) mockują tylko `RedisConnectionFailureException`, dlatego tego nie widać.
8. ~~Kosmetyka: komunikat „setting epoch” przy odczycie~~ — poprawione w GH-165 („reading epoch”).
9. ~~[#168] Reset hasła przy niedostępnym Redis nic nie unieważnia~~ — **rozwiązane w GH-168**: `confirm` fail-closed (503 przed zmianą hasła), `/activate` świadomie fail-open, listener best-effort z podwójnym czyszczeniem cache; zweryfikowane na `dev` 2026-11-23. Opis problemu dla kontekstu: `validateOneTimeToken` dzieli fail-open odczytów z `JwtAuthFilter`, więc `/password-reset/confirm` przy wstrzymanym Redis zwraca 200 i **zmienia hasło**, a potem: epoka resetu nie powstaje (inne linki działają), `onUserCredentialsChanged` przerywa się na pierwszej operacji Redis, więc **`revoke()` się nie wykonuje** (refreshe i sesje żyją, cache nie wyczyszczony), a link nie trafia na blacklistę. Nie regresja z #165 — przy odmowie połączenia było tak zawsze. Propozycja w issue: tryb „strict” (fail-closed, 503) dla tokenów jednorazowych; decyzja dla `/activate` otwarta.
