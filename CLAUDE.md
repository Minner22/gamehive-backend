# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Build, test, run (Maven via the **Maven Wrapper**; **JDK 25** required):

```bash
./mvnw clean install              # full build + tests
./mvnw test                       # all tests
./mvnw -Dtest=ClassName test                       # one test class
./mvnw -Dtest=ClassName#methodName test            # one test method
./mvnw spring-boot:run                             # run app (dev profile, default)
./mvnw spring-boot:run -Dspring-boot.run.profiles=prod
./mvnw -B verify                                   # what the CI `test` job runs
./mvnw -B sonar:sonar                              # what the CI `sonar` job runs (needs SONAR_TOKEN + target/ from verify)
```

**Maven Wrapper (GH-153)** pins **Maven 3.9.16** in `.mvn/wrapper/maven-wrapper.properties` (only-script mode — no `maven-wrapper.jar`, which `.gitignore` excludes anyway) together with `distributionSha256Sum`: a tampered or corrupted download fails instead of running. **Bumping Maven = new `distributionUrl` *and* a new SHA-256** (Maven Central publishes only `.sha512` — verify the zip with it, then compute the SHA-256 yourself). On Windows use `mvnw.cmd` from PowerShell/cmd and `./mvnw` from Git Bash. `.gitattributes` forces `mvnw`/`*.sh` to LF and `*.cmd` to CRLF — the repo runs with `core.autocrlf=true`, and a CRLF `mvnw` dies on the Linux runner with `/usr/bin/env: 'sh\r'`; `mvnw` also needs the executable bit in the index (`git update-index --chmod=+x mvnw` — Windows does not set it). **PowerShell splits unquoted `-Dkey=value` arguments at `.` and `,`** (`-Dmaven=3.9.16` arrives as `-Dmaven=3` + `.9.16`, `-Dtest=A,B` likewise) — quote them there (`"-Dtest=A,B"`); the commands above are Bash syntax. `sonar-maven-plugin` is pinned in `pluginManagement` and `sonar.projectKey` lives in `pom.xml`, so the short `sonar:sonar` prefix resolves to the pinned version and never runs inside `verify`.

The `dev` profile uses `spring-boot-docker-compose` which **auto-starts/stops `docker-compose.yml`** (PostgreSQL + Redis + Meilisearch) on app boot. Requires `secret.properties` (gitignored, holds the JWT secrets, the mail credentials and `gamehive.search.api-key`) and `.env` with `REDIS_PASSWORD`/`POSTGRES_PASSWORD`/`MEILI_MASTER_KEY` next to `pom.xml` — **`MEILI_MASTER_KEY` and `gamehive.search.api-key` must hold the same value**, one feeds the container, the other the client. The `test` profile needs neither — it uses H2 + embedded Redis (port 16379), disables search (`gamehive.search.enabled: false`) and overrides every JWT secret inline in `application-test.yml`.

## Architecture

Spring Boot 4 modular monolith. Java records for DTOs, Lombok everywhere, MapStruct for entity↔DTO mapping (binding via `lombok-mapstruct-binding` annotation processor).

### Module layout (`pl.m22.gamehive`)
- `auth/` — registration, login, JWT issuing/validation, password reset, account activation. `AuthController` is the only `/api/v1/auth/**` entry point.
- `user/` — `UserController` (self-service `/api/v1/users/me*`) and `AdminUserController` (`/api/v1/admin/users/**`, `@PreAuthorize("hasRole('ADMIN')")`). Domain split into `model/`, `repository/`, `service/`, `mapper/`, `dto/`, `util/`.
- `game/` — "Gry" phase (roadmap `docs/roadmap-games.md`): taxonomy dictionaries `Publisher`/`Category`/`Mechanic`/`Author` (#114) + `TaxonomyAdminController` (#115) + the `Game` entity with moderation workflow (#116) + the user side of submissions (#117): `GameController` (`/api/v1/games/**`) backed by `GameSubmissionService`, and a read-only `TaxonomyController` (`/api/v1/taxonomy/**`, any authenticated user — the id source for the submission form). Moderator decisions (#118): `GameModerationController` (`/api/v1/moderation/games/**`, MODERATOR/ADMIN) backed by `GameModerationService`, plus content-moderation audit in `game/event/` + `game/service/ContentModerationAuditService`. Expansions (#120) live in the **same `game/` package** (not a separate top-level module — they depend on `Game`, the taxonomy and the whole content-audit infrastructure), prefixed `GameExpansion*`: `GameExpansionController` (`/api/v1/expansions/**`) + `GameExpansionModerationController` (`/api/v1/moderation/expansions/**`). Full-text search (#122) is the subpackage `game/search/` — same reasoning as expansions: it indexes nothing but `game/` content; since #131 it also holds the taxonomy-autocomplete index behind `TaxonomyController`'s two `/suggest` endpoints. Same `model/`/`repository/`/`service/`/`mapper/`/`dto/`/`controller/`/`event/` split as `user/`.
- `collection/` — private per-user collection (#121). **A new top-level module, deliberately *not* inside `game/`** (unlike expansions in #120): it has no moderation workflow, no audit, no taxonomy — it only reads `Game`/`GameExpansion` and the viewer's identity. The dependency runs one way only (`collection` → `game`/`user`); nothing in `game/` knows collections exist. `CollectionController` (`/api/v1/collection/**`, any authenticated user) + `CollectionService`, plus `CollectionCleanupService`/`collection/event` for user-deletion cleanup. Same `model/`/`repository/`/`service/`/`mapper/`/`dto/`/`controller/`/`event/` split as `user/`.
- `common/` — `persistence/` (entity base hierarchy: generic `AbstractEntity<ID>` with auditing timestamps via `@PrePersist`/`@PreUpdate` and JPA-correct equals/hashCode by id; `LongEntity` = `@Id Long` IDENTITY, `UuidEntity` = `@Id UUID` via `@UuidGenerator(style = VERSION_7)`, `ModeratedLongEntity` = `LongEntity` + moderation-workflow fields, see "Games & moderation workflow"), `domain/` value objects, email service, logging (`LoggingAspect` wraps every `@RestController` for `Handled request:` lines + `CorrelationIdFilter` for MDC), and the exception infrastructure.
- `config/DevDataInitializer` — seeds two users (`john.doe@example.com` admin, `jane.smith@example.com` user, password `password123`) **only under `dev` profile**, then hands their UUIDs to `DevGameSeeder`. Tests rely on the same IDs/emails via `data.sql`.
- `config/DevGameSeeder` (`dev` only) — the game fixture: **18 APPROVED titles** (submitted and reviewed by the admin) **+ 3 submissions of `jane_smith` in PENDING / REJECTED / DRAFT**, so the moderation queue and "my submissions" are non-empty on a fresh volume. Called **straight from `DevDataInitializer.run`**, not as a second `ApplicationRunner` with `@Order` — it needs the users' UUIDs, so the ordering is a real dependency and belongs in the code; it therefore also runs inside that runner's transaction. It also seeds **12 expansions** (9 APPROVED + the same PENDING/REJECTED/DRAFT trio), hung off 8 of the base games and chosen to cover every case of the #120 override model — no override at all (pure inheritance), a single overridden player count, an overridden playing time, an overridden taxonomy — so the front has something to render `effective*` against. **Consequence to expect: those 8 base games can no longer be hard-deleted** (`GAME_HAS_EXPANSIONS`, 409); `Agricola`, `Azul`, `Splendor`, `Brass: Birmingham`, `Gloomhaven`, `Everdell` and the rest are deliberately left expansion-free for delete testing. Expansions are seeded **after** the games in the same pass (the base is resolved by title) and carry no publishers/authors/year — the #120 model has none. Idempotent **per title / per expansion name** (`GameRepository.findByTitle`, `GameExpansionRepository.findByName`), so a partial seed fills itself in — at the price that a game deleted by hand in dev comes back on the next boot (the alternative, "skip everything if the table is non-empty", would never top up). It deliberately bypasses `GameSubmissionService`/`GameModerationService` (a fixture is not a moderation decision), with two consequences: **no `content_moderation_audit_log` rows, and no `SearchIndexEvent` — Meilisearch stays empty until `POST /api/v1/admin/search/reindex`**. The seeder must **not** trigger that reindex itself: `ApplicationRunner` runs *before* `ApplicationReadyEvent`, which is exactly when `MeiliIndexInitializer` creates the index and applies its settings, so the call would hit an unconfigured index — hence a log line pointing at the endpoint instead. Publishers/authors created in flight inherit the game's fate (APPROVED game → APPROVED entry, otherwise PENDING — the same end state as `GameContentWriter` + the approve cascade); categories/mechanics are resolved **by name** against the V7 seed and a miss throws `IllegalStateException` (broken fixture, not a business error, so no `ErrorCode`). Note spring-boot-devtools is on the dev classpath: a `mvn compile` while the dev app runs hot-restarts it and re-runs the seeder.

### Security & JWT pipeline
- `SecurityConfig` is stateless (`SessionCreationPolicy.STATELESS`), CSRF disabled, only `/h2-console/**`, `/api/v1/auth/**`, `/swagger-ui/**`, `/v3/api-docs/**` are `permitAll`.
- **Filter order and registration (GH-163).** `CorrelationIdFilter` runs **before** the Security chain (`@Order(HIGHEST_PRECEDENCE + 1)` vs Security's `-100`; `+1` leaves first place to Boot's `CharacterEncodingFilter`), so every 401/403 the chain ends on its own (entry point `ACCESS_DENIED`, `JwtAuthFilter`'s `ACCOUNT_DISABLED`/`TOKEN_REVOKED`) carries `X-Correlation-Id` and the chain's logs carry `correlationId`. It is a `OncePerRequestFilter` with `shouldNotFilterErrorDispatch() = false` and keeps its id in a request attribute, so the ERROR dispatch to `/error` (which Tomcat performs *after* the original chain has unwound and cleared MDC) logs under the **same** id instead of none or a fresh UUID. **`JwtAuthFilter` runs only inside the Security chain**: being a `@Component` `OncePerRequestFilter`, Boot used to auto-register it a second time as a servlet filter (`LOWEST_PRECEDENCE`, all dispatcher types) — harmless only because `OncePerRequestFilter` skipped the second run. `SecurityConfig` now declares a `FilterRegistrationBean` with `setEnabled(false)`; **any new `@Component` filter meant for the Security chain needs the same**. Verified on `dev` (2026-11-22): both 401 kinds carry the header; a firewall-rejected URL (`;`, `%25` → `sendError(400)` → ERROR dispatch → 401) logs `Rejecting request…` and `Securing GET /error` under the same id as the response header.
- Custom `authenticationEntryPoint` returns **HTTP 401** (not Spring's default 403) with body `{"errorCode":"ACCESS_DENIED","message":"Authentication required"}`. Tests for unauthenticated requests must expect `isUnauthorized()`.
- `JwtAuthFilter` runs before `UsernamePasswordAuthenticationFilter`, **but `shouldNotFilter` skips `/api/v1/auth/{login,register,refresh}`** — those endpoints never touch the JWT filter.
- **`AuthServiceImpl.login` is enumeration-safe**: unknown e-mail and wrong password return the **same** `INVALID_CREDENTIALS` (401) — never `EMAIL_NOT_FOUND` (404). The password is verified **first and always**; for an unknown e-mail a `passwordEncoder.matches(...)` against a `@PostConstruct`-generated dummy bcrypt hash runs anyway, so response time is constant (no timing oracle). `USER_NOT_ACTIVATED` (403) is thrown **only after a correct password** — so account state leaks to the credential owner only, never to an unauthenticated prober. `login` does **not** go through an `AuthenticationManager`, and since GH-150 there is **no `AuthenticationProvider` bean**: Spring Security builds its (unused) global manager from the single `UserDetailsService` (`AppUserDetailsService`, which must stay — `UserAuthStateProvider` reads it and it keeps Boot from generating a default password). Re-adding a provider bean brings back the startup WARN from `InitializeUserDetailsBeanManagerConfigurer` (`security/AuthenticationManagerConfigTest`). **Every log line in `auth/` masks e-mails** with `LoggingUtils.obfuscateEmail` (null-safe → `<empty>`, so it can sit in a `catch` without masking the original failure).
- Four token types (`JwtTokenType`): `ACCESS` (15 min), `REFRESH` (7 days, cookie-only, scoped to `/api/v1/auth/refresh`), `ACTIVATION` (24 h), `PASSWORD_RESET` (15 min). Each has its own HS256 secret in `application*.yml` under `jwt.*.secret`.
- Refresh tokens are stored in Redis (`RedisRefreshTokenStore`) with a per-user cap (`maxActiveTokensPerUser: 5`). Used activation/password-reset/access tokens are blacklisted in Redis by JTI (`TokenBlacklistService`). Logout blacklists the access token AND calls `jwtService.revokeUsersTokens(email)` to invalidate every refresh.
- **Refresh tokens rotate, and reusing a rotated one logs the user out everywhere (GH-146).** `/refresh` goes through `JwtService.rotateRefreshToken(token, credentialsLoader)` — `validateToken(REFRESH)` checks only alg/signature/`exp`/type, **never Redis** — which verifies the token, loads the owner (the loader gets the e-mail of the *verified* token only), builds the new pair **before** touching Redis, and then runs one Lua script (`RedisRefreshTokenStore.rotate`): `DEL refresh_token:{old}` → on success `ZREM` the old JTI, `SET refresh_rotated:{old}` (value = email, TTL = the old token's remaining validity) **and store the successor** (`SET refresh_token:{new}` + `ZADD`) → `CONSUMED`; otherwise the marker decides between `REUSED` (rotated before → suspected theft) and `UNKNOWN` (evicted by the cap, logged out, revoked, never existed → plain `JWT_INVALID_JTI`, no global logout). **Check, consume and successor write must stay one atomic step.** A separate `exists` + `delete` lets two parallel refreshes both pass; an existence check before the script answers `JWT_INVALID_JTI` before the marker is ever looked at (that is why `existsByJti` was removed); and — the finding of the GH-146 security review, reproduced by `RefreshTokenReuseRaceTest` — writing the successor in a later step lets a thief send two parallel refreshes with one stolen token: the loser hits the marker and revokes everything it sees in the ZSET *before* the winner's successor lands there, so the owner is logged out everywhere while the thief keeps a working session. Building the access token before the script gives it `iat` ≤ rotation time < the epoch a concurrent reuse sets, so it dies too. `revokeAllByUserEmail` is a single script as well (`ZRANGE` + `DEL` in one step), which closes the same window for deactivation / force-logout / password change racing a refresh; it builds token keys from a prefix inside the script — fine on a single Redis, a Redis Cluster would need hash tags. `REUSED` logs WARN (obfuscated e-mail + JTI), publishes `RefreshTokenReuseDetectedEvent` and answers 401 **`REFRESH_TOKEN_REUSED`**; `UserSecurityEventListener` handles it with a plain synchronous **`@EventListener`** (there is no DB transaction on `/refresh`, so `@TransactionalEventListener` would silently never fire) that calls the same `revoke()` as force-logout — refresh tokens, session epoch, double cache eviction (GH-168). No audit row (no actor), incident in logs only. **No grace window**: concurrent refreshes are serialised by the frontend (gamehive-frontend#80, Web Locks + single-flight). Side effect: the cap of 5 now counts devices, not the last 5 refreshes. **Accepted risk, verified on `dev` (2026-11-24)**: a refresh whose outcome the client never learns — lost response, or a Redis timeout (`docker pause` → 503 in 2 s, and the script **ran after `unpause`**) — leaves the client with the old cookie, so its next refresh is a "reuse" and logs the user out on every device. Rotated markers also survive logout, so reusing a pre-logout token triggers the same global logout (correct: it is a reuse).
- **One-time e-mail links (ACTIVATION, PASSWORD_RESET) are single-use per user, not just per token** — a per-user epoch in Redis (`RedisSessionEpochStore`) on top of the JTI blacklist, checked in `AuthController.validateOneTimeToken` (shared by `/activate` and `/password-reset/confirm`: signature/type/exp → blacklist → `iat < epoch` → `TOKEN_REVOKED`). `activation_invalid_after:{email}` is set on activation resend; **`password_reset_invalid_after:{email}` (GH-145) is set on every reset request — before the token is generated, fail-closed (Redis down = no mail) — and after every successful reset** (`UserSecurityEventListener.onUserCredentialsChanged`, before the session revoke). Without it, every earlier reset mail stayed usable for 15 min, even after the owner had already reset the password with a newer link. Both epochs are **truncated to whole seconds** because `iat` is (an epoch in ms would revoke the token issued right after it); the price is a known, accepted window — a link issued in the very same second as the epoch stays valid. Reads are fail-open like the blacklist. Verified end-to-end on `dev` (2026-11-21): key truncated, TTL 900 s, stale link → `TOKEN_REVOKED`, reused link → `JWT_BLACKLISTED`, paused Redis → request still 200 and no mail.
- **Immediate token invalidation on deactivate / delete / password-change** (GH-63): `UserServiceImpl` (deactivate/delete/`deleteByEmail`) and `AuthServiceImpl.confirmPasswordReset` publish domain events in `user/event/`, handled by `UserSecurityEventListener` with `@TransactionalEventListener(AFTER_COMMIT)` — side effects fire only if the DB change actually commits. The listener revokes refresh tokens (`RedisRefreshTokenStore.revokeAllByUserEmail`), sets a **session epoch** (`RedisSessionEpochStore`, Redis key `token_invalid_after:{email}`, TTL = ACCESS validity), and evicts the auth-state cache. `UserReactivatedEvent` / `UserRolesUpdatedEvent` only evict the cache — they do **not** clear the epoch, so reactivation never resurrects old tokens (re-login required). **`/refresh` is the second line of defence (GH-172)**: the owner's data comes from `AuthService.loadRefreshCredentials`, which — before any rotation — answers 401 `ACCOUNT_DISABLED` for a disabled account and revokes all its refresh tokens best-effort (an `InfrastructureException` is logged at ERROR, the answer stays `ACCOUNT_DISABLED`, not 503). Without it, a refresh token that survived the deactivation (the listener's Redis steps are best-effort) could rotate forever and would wake up again after reactivation. Verified on `dev` (2026-11-24): a re-planted refresh key of a deactivated user → 401 `ACCOUNT_DISABLED`, no cookie, all keys + ZSET gone; after reactivation the old refresh → `JWT_INVALID_JTI`.
- `JwtAuthFilter` loads `{enabled, authorities, invalidAfter}` via `UserAuthStateProvider` (cached, see below) and itself writes the `ApiError` 401 body for two cases: disabled user → **`ACCOUNT_DISABLED`**, access token whose `iat` predates the epoch → **`TOKEN_REVOKED`**. The blacklist branch and every other invalid-token case instead fall through to the entry point's generic `ACCESS_DENIED`. The authenticated principal is the **email String** (downstream only uses `authentication.getName()`), not a `UserDetails`.
- **"Redis unavailable" = `RedisConnectionFailureException | QueryTimeoutException`, never the whole `DataAccessException` (GH-165).** A refused connection gives the first; a *hung* Redis (overload, network pause, `docker pause`) gives the second after `spring.data.redis.timeout` (2 s). Every Redis failure handler (`RedisSessionEpochStore`, `TokenBlacklistServiceImpl`, `RedisRefreshTokenStore`, `SearchReindexService` — and anything #146 adds) multi-catches both and keeps its own semantics (fail-open read / `REDIS_UNAVAILABLE` write / swallow). Before GH-165 only the first was caught, so a timeout meant 500 in `/activate`/`/password-reset/confirm`/`/refresh` and — via `JwtAuthFilter` — a silent 401 for every valid token. Not `DataAccessException`, because that also covers programming errors (`WRONGTYPE`, a failing Lua script, serialization) which must not silently and permanently switch off the blacklist; tests pin this both ways (`support/RedisUnavailability` + a `RedisSystemException` negative case). `JwtAuthFilter` now logs `ApplicationException` (bad/expired token) at DEBUG and **any other `RuntimeException` at ERROR with a stack trace** (still a 401 through the entry point) — an infrastructure failure must not look like a bad token. Verified on `dev` (2026-11-23, Redis paused): valid Bearer → 200 (was 401), `/refresh` → 503 `REDIS_UNAVAILABLE` (was 500). 
- **Behaviour per consumer while Redis is unavailable (GH-168)** — deliberate, do not unify:

  | Consumer | Mode | Why |
  |---|---|---|
  | `JwtAuthFilter` (blacklist, session epoch) | fail-open | a Redis blip must not log everyone out |
  | `/password-reset/confirm` (`isBlacklistedStrict`, strict reset epoch) | **fail-closed: 503 `REDIS_UNAVAILABLE` before the password changes** | its security effects (reset epoch, link blacklist, session revoke) all need Redis — before GH-168 it changed the password and revoked nothing |
  | `/activate` (blacklist, activation epoch) | fail-open | worst case is reusing a link that reached the owner's mailbox anyway; no access to another account, and fail-closed would block sign-ups |
  | writes (epochs, refresh store), `/refresh` | `REDIS_UNAVAILABLE` (503) | cannot verify/record; on `/refresh` (GH-146) a timeout leaves the rotation outcome unknown — the retry may land on `REFRESH_TOKEN_REUSED` |
  | `POST /auth/logout` (GH-148) | **503 `REDIS_UNAVAILABLE`, but the refresh cookie is cleared anyway** | both steps (`blacklistTokenStrict` of the access token, `revokeUsersTokens`) are attempted independently and any failure is reported — before GH-148 the blacklist failure was swallowed (silent partial logout) and the revoke failure aborted before the cookie was cleared |
  | `UserSecurityEventListener` | best-effort per step | see below |

  `validateOneTimeToken` takes the blacklist check as a `Predicate`, so each call site picks its mode; the password-reset epoch is strict because its only reader is `confirm`. A refused `confirm` burns nothing — the same link works once Redis is back. **`UserSecurityEventListener.revoke()` evicts `userAuthState` before the Redis steps (so a deactivation bites at once from the DB even with Redis down), runs each Redis step in `bestEffort` (catches only `InfrastructureException`, logs ERROR, continues) and evicts again in `finally`.** The second eviction is load-bearing: the cached state holds the **session epoch**, so a request that reloads it between the first eviction and `invalidateNow` would cache the *old* epoch for the full 60 s TTL and keep a stolen token alive after force-logout / password change. The security review of GH-168 caught exactly that regression in the first version of the change (evict-first only); `UserSecurityEventListenerTest.staleAuthState*` reproduces it with a real `ConcurrentMapCache`. **Logout puts the cleared cookie on `HttpServletResponse` before the Redis steps** (right after `validateToken` — an invalid token still gets a plain 401 without touching the cookie, deliberately): `DispatcherServlet.processHandlerException` calls `resetBuffer()`, not `reset()` (checked in spring-webmvc 7.0.6), so headers set on the raw response survive into the `GlobalExceptionHandler` error response, while headers on a `ResponseEntity` that was never returned are lost — use this instead of building error bodies in a controller. **A Redis timeout means "outcome unknown", not "not done"**: verified on `dev` (2026-11-23) that a `SET` sent to a paused Redis is executed after `unpause` — the logout that answered 503 had in fact blacklisted the access token, whereas the refresh revoke (which needs a `ZRANGE` result first) never ran. So treat `REDIS_UNAVAILABLE` after a write as "may or may not have been applied"; every write here is idempotent and safe to retry. Verified on `dev` (2026-11-23, Redis paused): `confirm` → 503 in 2 s and the old password still works, no `PASSWORD_CHANGE` audit, the same link succeeds after unpause; Bearer → 200; `/activate` → 200.
- Per-request user state is cached in-memory via Caffeine (`userAuthState`, 60 s TTL, `CacheConfig`) — the TTL is only a safety net; every mutation evicts the entry immediately. Caffeine is per-instance: under horizontal scaling staleness is bounded by the TTL (full consistency would need a Redis-backed cache / pub-sub eviction).

### Audit log
- **Persistent audit of account mutations** (who/whom/what/when): `UserServiceImpl` (`updateUserRoles` → `ROLE_CHANGE`, plus `DEACTIVATE` / `ACTIVATE` / `DELETE` / `FORCE_LOGOUT`) and `AuthServiceImpl.confirmPasswordReset` (`PASSWORD_CHANGE`, self-service so `actor == target`) publish a **dedicated `UserAuditEvent`** — separate from the GH-63 security events, so `UserSecurityEventListener` stays untouched. `activateUser` takes a `requesterEmail` purely to record the actor (no new guard).
- `AuditLogEventListener` (`@TransactionalEventListener(AFTER_COMMIT)`) delegates to `AuditLogService.record`, which is **`@Transactional(REQUIRES_NEW)`** — a new tx is mandatory because AFTER_COMMIT runs after the business tx already committed/closed, and it must be a **separate bean** (self-invocation would bypass the proxy). Consequence: an audit-write failure does **not** roll back the business action (logging never blocks it); a rolled-back action never delivers the event → no entry (so "exactly one entry per committed action").
- `UserAuditLogEntry` (`LongEntity`, table `user_audit_log`, migration `V4`) has **no FK to `application_users`** — entries must survive a user `DELETE`, so `targetId` / `targetEmail` / `actor` are copied values, not relations. `created_at` (from `AbstractEntity`) is the "when". `details` is nullable `text` — only `ROLE_CHANGE` fills it, with before/after role names as small hand-built JSON (roles are a controlled `ROLE_*` vocabulary, no escaping needed). `correlationId` is snapshotted from MDC (`CorrelationIdFilter.CORRELATION_ID`) at publish time to link the entry to request logs. **GH-144: `CorrelationIdFilter` keeps a client-supplied `X-Correlation-Id` only if it matches `[A-Za-z0-9._-]{1,64}` and otherwise substitutes a fresh UUID** (in MDC, the response header and the audit row alike; never a 400). Before that, a value over 64 characters returned 2xx, but the audit insert into `correlation_id VARCHAR(64)` failed inside `REQUIRES_NEW` after commit and Spring only logged it. The entry silently vanished, so an admin or moderator could erase their own action from the audit with one header. `MAX_CORRELATION_ID_LENGTH` is wired into both audit entities' `@Column(length = …)`, so raising it needs a new `V*` for V4/V10. Any other client-controlled value headed for an audit column must likewise fit before it is published (details in skill `common-expert`). Entity + `AuditAction` enum live in `user/model` (coverage-excluded); service in `user/service`, event + listener in `user/event`.

### Games & moderation workflow (GH-114…GH-120, GH-138) — details in skill `moderation-workflow`
Full design notes (entity shapes, endpoints, guards, ErrorCodes, override model of expansions, fixture history) live in **`.claude/skills/moderation-workflow/SKILL.md`** — load it before touching `game/` (outside `game/search/`). Cross-cutting rules worth knowing everywhere:
- **One entity with a status** (`ModeratedLongEntity` in `common/persistence`, shared by `Game` and `GameExpansion`): library = `APPROVED`, "my submissions" = own `DRAFT/PENDING/REJECTED`. Transitions live on the base class; the status guards that map to `ErrorCode`s live in the services.
- **No FK to `application_users`** for `submittedBy`/`reviewedBy` (same convention as both audit logs and collections) — content and audit survive a user `DELETE`.
- **Enumeration-safe reads**: someone else's non-APPROVED game/expansion is `*_NOT_FOUND`, never a "not owner" code. Known, accepted exceptions: expansion-create and collection-add answer `*_NOT_APPROVED` (409).
- Game/expansion services **return DTOs, not entities** (LAZY collections, mapping inside the transaction; `hibernate.default_batch_fetch_size: 20` instead of multi-collection `@EntityGraph`).
- Content-moderation audit mirrors the user audit exactly (`@TransactionalEventListener(AFTER_COMMIT)` → separate `REQUIRES_NEW` bean); games and expansions share the table but not the id sequence → use `findByTargetTypeAndTargetId`.
- `EXPANSION_*` ErrorCodes **mirror** the `GAME_*` ones instead of reusing them; delete of a game with expansions is blocked (`GAME_HAS_EXPANSIONS`) with FK `RESTRICT` as the second line of defense — the project-wide "service guard + DB RESTRICT" shape.
- Moderation queues take `ModerationQueueStatus` (PENDING/REJECTED only), **not** `ModerationStatus` — do not "unify" it with the taxonomy `?status=`.
- Resubmission limit `gamehive.moderation.max-resubmissions`: **5** in `application.yml`, **2** under `test`.

### Error handling

All thrown errors extend `BaseException(ErrorCode)`. The three subclasses determine **log level only** — HTTP status comes from `ErrorCode.httpStatus` regardless of subclass. Pick the subclass by what kind of failure it is:

- **`DomainException`** — business rule / invariant violated. Logged at INFO.
  Examples: `EMAIL_ALREADY_EXISTS`, `INVALID_PASSWORD`, `CANNOT_REMOVE_LAST_ADMIN`.
- **`ApplicationException`** — use-case flow problem: lookup miss, token validity, precondition not met. Logged at WARN.
  Examples: `USER_NOT_FOUND`, `JWT_EXPIRED`, `JWT_BLACKLISTED`.
- **`InfrastructureException`** — external system or technical layer failed (Redis, SMTP, crypto). Logged at ERROR with stack trace. Always wraps a caught third-party exception.
  Examples: `REDIS_UNAVAILABLE`, `EMAIL_SEND_FAILED`, `JWT_SIGNING_ERROR` (JOSE).

**`ApiError.message` is always `ErrorCode.defaultMessage` (GH-149).** The message passed to `BaseException(ErrorCode, String)` is a **log detail only**: the Domain/Application/Infrastructure handlers log it at their level and answer with `error(ex.getErrorCode())` — no exception message ever reaches the client. Before GH-149 `buildResponse` copied `ex.getMessage()` into the body, so every `throw new …Exception(CODE, "… " + data)` reflected request data (masked e-mails, usernames) or library internals (`Failed to parse JWT: <Nimbus message>`) back to the caller. So: put whatever context helps diagnosis into the message (ids, token type, the library's message) but **mask e-mails** (`Email.obfuscated()` / `LoggingUtils.obfuscateEmail`) — logs are data too; and give every `ErrorCode` a meaningful `defaultMessage`, because that is the only text a client sees. **User-facing text is the frontend's job**: it maps `errorCode` to Polish messages (gamehive-frontend#81) and falls back to a generic message for an unknown code; `message` is developer information. Field messages in `ApiValidationError` are untouched (already static). Pinned by `GlobalExceptionHandlerTest.baseException_respondsWithDefaultMessage_logsDetail` and end-to-end by `common/exception/ApiErrorStaticMessageTest` (cases from the issue, each also asserting the detail survives in the log). Verified on `dev` (2026-11-25): duplicate username/e-mail, unknown-e-mail login and a garbage refresh cookie all answer with the bare `defaultMessage`, while the log keeps `john_doe`, `jo******@example.com` and Nimbus' `Missing part delimiters`.

`ErrorCode.java` is grouped into sections (`Domain` / `Application` / `Infrastructure` / `Handler-only`) matching this taxonomy — the section a code lives in tells you which exception class to throw. Adding a new failure mode means: (1) add an `ErrorCode` entry in the matching section with its `HttpStatus`, (2) throw the matching exception subclass. `GlobalExceptionHandler` dispatches by subclass to apply the right log level; the response body (`ApiError(code, message)`) is identical regardless of subclass.

The eight "Handler-only" codes (`ACCESS_DENIED`, `DATA_CONFLICT`, `VALIDATION_ERROR`, `INTERNAL_ERROR`, plus the four routing ones from GH-140 below) are never thrown directly — they're used by `GlobalExceptionHandler` when wrapping framework exceptions (`AuthorizationDeniedException`, `MethodArgumentNotValidException`, `MethodArgumentTypeMismatchException` → 400 `VALIDATION_ERROR` for malformed path vars such as a bad UUID **or a value outside a bound enum such as `?status=DRAFT` (#138)**, `PropertyReferenceException` → 400 `VALIDATION_ERROR` for an unknown property in `?sort=` (GH-138: Spring Data raises it at query execution, *outside* argument binding, so without this handler a client's typo fell through to the `Exception` fallback and answered **500** with an ERROR-level stack trace — on all 12 paginated endpoints, not just the moderation queues; note the class lives in `org.springframework.data.core` since Spring Data Commons 4, not the pre-Boot-4 `org.springframework.data.mapping`), `DataIntegrityViolationException` → 409 `DATA_CONFLICT` — the backstop for race conditions: publisher/author find-or-create losing to a concurrent insert on the UNIQUE constraint, or a `*_IN_USE` delete guard losing a TOCTOU race against the FK RESTRICT — and the fallback `Exception`).

**GH-140 — routing-level client errors.** Until #140 *every* request Spring MVC could not match fell through to `@ExceptionHandler(Exception.class)` and answered **500 `INTERNAL_ERROR` with an ERROR-level stack trace**: wrong method, unknown path, wrong `Content-Type`, missing required `@RequestParam`. Two costs, both real: the client could not tell its own typo from an outage, and any scanner buried the ERROR channel in fake incidents. Four handlers close it, all logging at **WARN without a stack trace** (same shape as every other client error here):

- `HttpRequestMethodNotSupportedException` → 405 `METHOD_NOT_ALLOWED` **plus an `Allow` header** built from `ex.getSupportedHttpMethods()`, which is `@Nullable` (the one-arg constructor leaves it null). The guard before `headers.setAllow(...)` exists to avoid emitting an **empty** `Allow:` header — `setAllow(null)` does *not* throw (`StringUtils.collectionToCommaDelimitedString(null)` returns `""`), so a test asserting `getHeaders().getAllow()` cannot see the difference and must assert `containsHeader(ALLOW)` instead;
- `NoResourceFoundException` **and** `NoHandlerFoundException` → 404 `RESOURCE_NOT_FOUND`, one handler for both. **Deliberately a different code than the domain `*_NOT_FOUND`** — "no such path" is not "no such game". Which of the two actually flies depends on `spring.web.resources.add-mappings`: at its default (true, and the project overrides nothing) an unmatched path reaches `ResourceHttpRequestHandler` and raises the first; with the property off it is the second, and handling only one would silently drop 404 back to 500;
- `HttpMediaTypeNotSupportedException` → 415 `UNSUPPORTED_MEDIA_TYPE`;
- `ServletRequestBindingException` → 400 `VALIDATION_ERROR`, covering a missing required param or header in one handler. Two subclasses deliberately escape it, both because Spring picks the most specific match: `MissingRequestCookieException` keeps `REFRESH_TOKEN_MISSING` (the regression net is end-to-end in `AuthControllerTest`, "GET /refresh bez cookie → 401" — never a direct handler call, which cannot prove which handler Spring would choose), and **`MissingPathVariableException` keeps 500 `INTERNAL_ERROR` logged at ERROR with a stack trace**. That one is not a client error at all: it means a handler declares an `@PathVariable` the mapping template does not contain, i.e. a defect in our own code, and Spring itself reports it as 500. Blaming the caller with a 400 at WARN would hide exactly the bug worth seeing.

**`HttpMediaTypeNotAcceptableException` → 406 `NOT_ACCEPTABLE`, and — the part that matters far beyond 406 — every error response in this class is built through the private `errorBuilder(ErrorCode)`, which pins `.contentType(APPLICATION_JSON)`.** This is the fix for a symptom that looks unrelated: `Accept: application/xml` used to answer **401 `ACCESS_DENIED`**. The chain — the advice returns its `ApiError`, writing it finds no converter the client accepts, `ExceptionHandlerExceptionResolver` gives up and returns null, `DefaultHandlerExceptionResolver` falls back to `response.sendError(...)` (a domain exception escapes the `DispatcherServlet` outright instead), the container ERROR-dispatches to `/error`, Spring Security runs there too (`spring.security.filter.dispatcher-types` defaults to `async, error, request`), `JwtAuthFilter` is skipped because `OncePerRequestFilter.shouldNotFilterErrorDispatch()` is true, and `/error` is not `permitAll` → entry point → 401. An explicit `contentType` on the `ResponseEntity` skips content negotiation at write time, so the body goes out and `/error` is never reached. **Pinning it on only one handler is not enough** — that was the first attempt, and it left 405/404/415 answering with an empty body and every `DomainException` still escaping; keep new handlers going through `errorBuilder`. **`/error` is deliberately NOT added to `permitAll`** — that would mask the symptom and expose Boot's default error JSON (exception class, message, path) to unauthenticated callers for every future escaped exception.

**What the suite cannot prove here:** MockMvc has no container, so it never performs an ERROR dispatch — `RoutingErrorMappingTest` pins the target state (406 + `ApiError`), but the *disappearance* of the misleading 401 is only verifiable by hand on `dev`. The OpenAPI contract is untouched by #140: the spec does not document 405/415/406 on individual endpoints even though the API now returns them.

### API documentation (OpenAPI/Swagger)
- springdoc-openapi (`springdoc-openapi-starter-webmvc-ui`) generates the spec. Global metadata + the `bearerAuth` security scheme (HTTP/bearer/JWT) live in `config/OpenApiConfig` (`@OpenAPIDefinition` + `@SecurityScheme`); `config` is coverage-excluded. UI at `/swagger-ui.html`, raw doc at `/v3/api-docs` (both already `permitAll` in `SecurityConfig`). **Disabled under `prod`** via `springdoc.api-docs.enabled=false` / `swagger-ui.enabled=false` in `application-prod.yml`.
- Convention: each controller has a `@Tag`; secured controllers carry class-level `@SecurityRequirement(name = "bearerAuth")` (auth endpoints are public, so no requirement). Endpoints use `@Operation` + **repeatable `@ApiResponse`** — `@ApiResponse` is `@Repeatable`, so the `@ApiResponses({...})` wrapper is redundant (Sonar `java:S1710`) and GH-136 removed all 65 of them; springdoc reads both forms identically, so **do not reintroduce the wrapper**. Error bodies reference `@Schema(implementation = ApiError.class)` (or `ApiValidationError.class` for 400). `AdminUserController` declares the shared 401/403/500 responses **once at class level** (springdoc merges them with method-level ones) — follow that pattern instead of repeating common codes per method. That merge is what the wrapper removal could have silently broken (a lost 401/403/500 on ~40 endpoints, with every test still green), so `OpenApiDocumentationTest` now pins it on `SearchAdminController` and `AdminUserController` — the 503 assertion is the decisive one, since springdoc has no default that would produce it.
- Request/response DTOs are documented with `@Schema` on record components (`dto` is coverage-excluded). Auth success bodies use dedicated records `AccessTokenResponseDto` (login/refresh) and `MessageResponseDto` (register/activate) — added so the spec has real schemas instead of raw `Map`/`String`. Note: `register`/`activate` therefore return `application/json`, not `text/plain`. Paginated endpoints document their 200 body with dedicated flat `Page*Dto` records (`PageUserResponseDto`, `PageAuditLogResponseDto`, `PageGameDto`, `PageGameModerationDto`, `PageGameExpansionDto`, `PageGameExpansionModerationDto`, `PageGameCollectionItemDto`, `PageExpansionCollectionItemDto`, `PageSearchResultDto`, `PagePublisherDto`, `PageAuthorDto`) instead of the weak auto-schema for `Page<T>`. The reject-request body is a single `RejectContentRequestDto` (`{reason}`) shared by both moderation controllers — renamed from `RejectGameRequestDto` in GH-120, which touched no test since they all post raw JSON.
- The `OpenApiDocumentationTest` smoke test asserts `/v3/api-docs` returns 200 with the expected title, the `bearerAuth` scheme, and key paths — keep it green when changing OpenAPI config. Since GH-131 it also pins which endpoints are flagged `deprecated`: the growing taxonomy lists yes, the curated `categories`/`mechanics` no.
- **Deprecating an endpoint** = three things, all deliberate: Java `@Deprecated(since = "GH-<issue>")` on the handler, `@Operation(deprecated = true, ...)` with a description saying what to use instead and what the caller loses by staying, **and** a Javadoc block whose `@deprecated` tag `{@link}`s the successor (without it Sonar raises `java:S1123`) — see the two taxonomy lists. **springdoc does not read Javadoc** (no `springdoc-openapi-starter-common`, no javadoc plugin), so the tag is for readers of the code only; the spec description still comes from `@Operation` alone. The test only pins the resulting `deprecated: true` in the spec, not which annotation produced it. `java:S1133` ("remove this deprecated code someday") fires regardless and is marked Won't fix in SonarCloud — a deliberate deprecation cannot silence it.

### HTTP compression (GH-143)
- `server.compression` in `application.yml` (both profiles): gzip for `application/json`, `text/*` and JS when the client sends `Accept-Encoding: gzip`. Measured on `dev` (2026-11-21): `GET /games?size=20` 12 679 → 3 525 B, `/games/search?q=a&size=12` 8 616 → 2 492 B, `swagger-ui-bundle.js` 1.5 MB → 413 kB; clients without `Accept-Encoding` get plain JSON; 204s are untouched.
- **`min-response-size: 2KB` does NOT apply to controller responses — deliberate, accepted.** Spring MVC flushes the body before the response ends, so it goes out as `Transfer-Encoding: chunked` with no `Content-Length`, and Tomcat only honours the threshold when the length is known. Every MVC response is therefore gzipped, including small ones and the access-token body of `/auth/login`/`/auth/refresh`. The threshold still applies to bodies written in one go with a known length (the Security entry point's 401, static resources). Decision: keep it that way — gzip on a small JSON is negligible, and BREACH does not apply here (the token responses reflect no attacker-controlled input; the refresh cookie is `SameSite=Strict`). Do not "fix" it with a buffering filter that sets `Content-Length` without revisiting that trade-off; `HttpCompressionTest` pins both behaviours.
- MockMvc bypasses the Tomcat connector, so compression is only testable on a real port (`HttpCompressionTest`, the project's first `RANDOM_PORT` test — see skill `testing-expert`).

### Persistence
- Prod: PostgreSQL with **Flyway** (`src/main/resources/db/migration/V*__*.sql`). `ddl-auto: none` — schema changes go through new `V*` files. **Spring Boot 4 split auto-config into per-tech modules — Flyway runs only with the `spring-boot-starter-flyway` dependency; bare `flyway-core` no longer self-configures (migrations silently won't run).**
- **Never edit a `V*` file that has already been applied to a database** — fix forward with a new `V*` instead. Flyway stores a checksum per applied migration and refuses to boot on mismatch (`FlywayValidateException: Migration checksum mismatch`). This bit once already: `d7a981d` ("GH-116 poprawki po CR") appended four `CREATE INDEX` to an already-applied `V8`, which left the dev DB stuck at V8 for five weeks and silently missing those indexes plus V9/V10/V11. Recovery on a dev box is `docker compose down -v` + restart (drops the named volume — `docker compose down` alone keeps it, so the error just repeats); `flyway repair` only rewrites the checksum and would leave the amended statements permanently unapplied.
- **A green `mvn test` proves nothing about migrations.** The `test` profile disables Flyway and lets Hibernate generate the schema, so `V*` files are never executed there — checksum drift, broken DDL, `ON DELETE CASCADE`, indexes and column DEFAULTs are all invisible to the suite. (The one exception is a cascade *also* declared on the entity via `@OnDelete`, as in V12's collection tables — Hibernate then puts it into the H2 schema as well, so the behaviour, though not the migration file, is covered.) **That holds for the local `./mvnw test` only — since GH-154 the CI proves it.** Job **`integration`** (`./mvnw -Pintegration test`) runs `migration/FlywayPostgresMigrationTest` (`@Tag("postgres")`) on a real **PostgreSQL 16** (Testcontainers, `postgres:16-alpine` — the same image as `docker-compose.yml`, bump both together): every `V*` applied to an **empty** database, then **`ddl-auto=validate`** compares each entity with the migrated schema (a missing or renamed column fails the context), plus SQL assertions on what lives only in migrations — the `ON DELETE` rules (CASCADE for join/collection tables and `user_roles`, deliberately none for `game_expansions.base_game_id` and the dictionary FKs, the second line behind `GAME_HAS_EXPANSIONS`/`*_IN_USE`) and the indexes (including the ones `d7a981d` once appended to an applied `V8`). The migration count comes from the classpath, so a new `V13` needs no test change. Profile `it-postgres` (`src/test/resources/application-it-postgres.yml`) is layered **on top of** `test` (`@ActiveProfiles({"test", "it-postgres"})`): embedded Redis, `SyncTaskExecutor` and JWT secrets stay, while Flyway goes on, `validate` replaces `create-drop`, `data.sql` is off and the connection comes from `@ServiceConnection`. The `postgres` tag is excluded by default (`<excludedGroups>` in `pom.xml`), so a plain `./mvnw test` still needs no Docker; `-Pintegration` flips the filter and runs only those tests (needs Docker Desktop locally). Deliberately **no** `@Testcontainers(disabledWithoutDocker = true)` — a missing Docker in CI must redden the job, not skip it. Job **`migrations-guard`** (PRs only) fails on any change to `src/main/resources/db/migration` other than an added file (`git diff --name-status origin/<base>...HEAD`, anything not `A` → `::error` annotation on the file) — the `d7a981d` mistake now stops at the PR. Its step needs `shell: bash`: the default `run` shell is `bash -e` **without `pipefail`**, so a failing `git diff` piped into `awk` would pass silently (found during the GH-154 verification). Verified 2026-11-24 on a throwaway draft PR: a new `V13` passes the guard and `integration` applies 13 migrations; an edited `V1` → red guard with the file annotated; an entity field without a migration → red `integration` (`Schema validation: missing column`) while `test` stays green; a broken base ref → red guard. Booting `dev` is still the check for `DevGameSeeder` data, Meilisearch and anything that needs the whole stack.
- Test: H2 in PostgreSQL-compat mode, `ddl-auto: create-drop`, **Flyway disabled**, `data.sql` populates fixtures (`schema-locations: []` is intentional — Hibernate creates the schema, only data.sql runs).
- `AppUser` ↔ `UserRole` is many-to-many through `user_roles` join table. `UserRole.name` values are stored with the `ROLE_` prefix (e.g. `ROLE_ADMIN`, `ROLE_USER`).
- `AppUser` uses a **UUID v7** primary key (`UuidEntity`, `@UuidGenerator(style = VERSION_7)`; id assigned in-memory at `persist()` — no DB round-trip). Every other entity keeps `Long` IDENTITY (`LongEntity`). FKs to `application_users` (e.g. `user_roles.user_id`) are `uuid`. `V3__migrate_app_user_to_uuid.sql` converts the schema via **drop & recreate** (truncates `application_users`/`user_roles`) — destructive, valid only because there is no production data.

## CI

GitHub Actions workflow **`CI`** (`.github/workflows/ci.yml`, GH-153; replaced the single-job `build.yml`) runs on every PR, on pushes to `master` and on demand, with **two jobs**:

- **`test`** — `./mvnw -B verify` (a required check of the `master` ruleset, GH-157). Always uploads `target/surefire-reports/` as artifact **`surefire-reports`** (7 days) — after a red run, download it (`gh run download <run-id> -n surefire-reports`) instead of scrolling the log. On success it also uploads **`sonar-input`** (1 day): `target/classes`, `target/test-classes`, `target/site/jacoco/jacoco.xml`, `target/surefire-reports` of *that* commit.
- **`integration`** (GH-154) — in parallel with `test`: `./mvnw -B -Pintegration test`, the Flyway/PostgreSQL check described under "Persistence"; on failure uploads `surefire-reports-integration`.
- **`migrations-guard`** (GH-154, PRs only) — blocks edits, deletions and renames of existing `V*` files; only new migrations pass.
- **`sonar`** — `needs: test`; the only job with `fetch-depth: 0`; restores `sonar-input` into `target/` (default paths, so no `sonar.java.binaries`/`xmlReportPaths` settings) and runs `./mvnw -B sonar:sonar` without rebuilding or re-testing. **Skipped for Dependabot and fork PRs** (they get no `secrets.*`; the `secrets` context is not allowed in a job-level `if:`, hence the condition on actor and head repo) — skipped, not red. An expired or broken `SONAR_TOKEN` now reddens only `sonar` (`HTTP 403 … check … SONAR_TOKEN`), while `test` stays green (#152 used to redden everything).

`permissions: contents: read`, `persist-credentials: false` on checkout (nothing pushes), `timeout-minutes` per job. `concurrency` cancels the previous run of the same PR on a new push, but **never cancels `master` runs** (every merge gets a full analysis). Maven deps cached by `setup-java` (`cache: maven`); the Sonar cache key depends on `pom.xml` (it used to be a constant that never refreshed). Actions are pinned by major (`checkout@v7`, `setup-java@v6`, `upload-artifact@v7`, `download-artifact@v8` — which fails on an artifact digest mismatch by default, `cache@v6`); SHA pinning is deferred to #156. Verified 2026-11-24 on a throwaway draft PR: both jobs green (`test` 1:41 vs ~2:42 for the old single job), the old run cancelled by a second push, a deliberately red test → `test` failure + `sonar` skipped + `surefire-reports` with the failure, a bad token → `test` green + `sonar` red; coverage import unchanged versus `master`. The Dependabot skip is verified live (2026-11-25, the first four Dependabot PRs #182–#185): `sonar` shows as *skipping*, `test`/`integration`/`migrations-guard` green; the fork-PR branch of the condition is still unverified (no fork PR yet).

**Dependabot (GH-155, `.github/dependabot.yml`)** — weekly (Monday, Europe/Warsaw), max 5 open PRs per ecosystem, labels `type:chore` + `area:ci`, commit prefixes `deps` (Maven) / `ci` (actions); deliberately no `GH-<nr>` prefix, a bot has no issue. Maven groups, **matched in order, first match wins** (so the catch-all must stay last): `spring-boot` (`org.springframework.boot*`, i.e. the parent — every starter takes its version from it), `meilisearch` (the SDK only), `maven-plugins` (jacoco, sonar, `org.apache.maven.plugins`), `libraries` (`*`). **`com.squareup.okhttp3:*` is ignored (GH-190)**: the first Dependabot round (#183) bumped `meilisearch-java` 0.21.0 → 0.22.1 *and* `okhttp.version` 5.3.2 → 5.5.1, while the 0.22.1 POM still declares okhttp 5.3.2 — Dependabot proposes the newest okhttp, not the one the SDK needs, and a group only bundles the two bumps into one PR. So `okhttp.version` moves by hand with an SDK bump (procedure in skill `search-meili`). The former `test` group (`dependency-type: development`) was dropped in GH-190: Dependabot counts Maven **plugins** as development dependencies, so it swallowed jacoco/sonar ahead of `maven-plugins` regardless of group order (#184); test libraries now land in `libraries`. GitHub Actions: one group. **Major Boot upgrades are ignored** — a Boot major is a migration with its own issue, not a bump. Two `pom.xml` properties exist so that a bump can never move one half of a pair: **`okhttp.version`** (see the search section — the property keeps `okhttp` == `okhttp-jvm`, the `ignore` keeps it in step with the SDK) and **`mapstruct.version`** (`mapstruct` + `mapstruct-processor` in `annotationProcessorPaths` — an API/processor mismatch breaks the generated mappers). Merging a `spring-boot` or `meilisearch` group PR still needs `verify-dev`: the suite runs Meili's fallback, so a broken SDK/okhttp pair stays green in `test`. The config is validated by GitHub only on `master` (*Insights → Dependency graph → Dependabot*).

**`master` is protected by a ruleset (GH-157)**, kept as code in `.github/rulesets/master.json` — GitHub does not read that file, it is the reviewable source of truth; apply a change with `gh api -X PUT repos/Minner22/gamehive-backend/rulesets/<id> --input .github/rulesets/master.json` (`gh api repos/Minner22/gamehive-backend/rulesets` lists the id). Rules: changes only through a PR (0 approvals — one-person project), **required checks `test`, `integration`, `migrations-guard`** pinned to the GitHub Actions app (`integration_id: 15368`, so no other app can satisfy a check of the same name), no force-push, no branch deletion, merge commits only (`allowed_merge_methods: ["merge"]`, matching the history). **`sonar` is deliberately not required** — a SonarCloud outage or an expired token must not block merging. `migrations-guard` runs on PRs only, which is exactly what the ruleset covers; a job skipped by its `if:` counts as passed. `strict_required_status_checks_policy: false`: the branch need not be up to date with `master` (CI already builds the merge commit; strict mode would mean a rebase per Dependabot PR). **Repository admins bypass only in `pull_request` mode** — `gh pr merge --admin` can land a PR over a red check in a CI emergency, but a direct `git push` to `master` is rejected for admins too. **Renaming a job in `ci.yml` = update the ruleset first**: a required check that never reports blocks every merge. `delete_branch_on_merge: true`; the local `.git/hooks/pre-commit` (blocks commits on `master`, unversioned) stays as an earlier signal. Verified 2026-11-25 with a copy of the ruleset on a throwaway branch: direct push, force-push and deletion → `GH013` (admin account); draft PR with a red `test` → `BLOCKED`; draft PR with only `sonar` red → `UNSTABLE` (mergeable); then on `master` itself a direct push → `GH013 … Changes must be made through a pull request`. Pitfall met on the way: a plain YAML scalar containing `: ` (`run: echo "X: y"`) makes the whole workflow invalid — GitHub then records a 0-second failed run and starts **no** checks for the PR, which a required check turns into a silent block.

 **PRs are built against a merge commit (branch + master)**, so if master moved ahead, local-only `mvn test` may pass while CI fails — pull/rebase master before debugging green-local/red-CI failures. SonarCloud coverage excludes `dto`, `model`, `config`, `mapper`, `exception`, `logging` packages and `GameHiveApplication`.
