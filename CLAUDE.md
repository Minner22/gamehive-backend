This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Build, test, run (Maven; **JDK 25** required):

```bash
mvn clean install              # full build + tests
mvn test                       # all tests
mvn -Dtest=ClassName test                          # one test class
mvn -Dtest=ClassName#methodName test               # one test method
mvn spring-boot:run                                # run app (dev profile, default)
mvn spring-boot:run -Dspring-boot.run.profiles=prod
mvn -B verify org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
    -Dsonar.projectKey=Minner22_gamehive-backend   # CI equivalent (SonarCloud)
```

The `dev` profile uses `spring-boot-docker-compose` which **auto-starts/stops `docker-compose.yml`** (PostgreSQL + Redis + Meilisearch) on app boot. Requires `secret.properties` (gitignored, holds the JWT secrets, the mail credentials and `gamehive.search.api-key`) and `.env` with `REDIS_PASSWORD`/`POSTGRES_PASSWORD`/`MEILI_MASTER_KEY` next to `pom.xml` — **`MEILI_MASTER_KEY` and `gamehive.search.api-key` must hold the same value**, one feeds the container, the other the client. The `test` profile needs neither — it uses H2 + embedded Redis (port 16379), disables search (`gamehive.search.enabled: false`) and overrides every JWT secret inline in `application-test.yml`.

## Architecture

Spring Boot 4 modular monolith. Java records for DTOs, Lombok everywhere, MapStruct for entity↔DTO mapping (binding via `lombok-mapstruct-binding` annotation processor).

### Module layout (`pl.m22.gamehive`)
- `auth/` — registration, login, JWT issuing/validation, password reset, account activation. `AuthController` is the only `/api/v1/auth/**` entry point.
- `user/` — `UserController` (self-service `/api/v1/users/me*`) and `AdminUserController` (`/api/v1/admin/users/**`, `@PreAuthorize("hasRole('ADMIN')")`). Domain split into `model/`, `repository/`, `service/`, `mapper/`, `dto/`, `util/`.
- `game/` — "Gry" phase (roadmap `docs/roadmap-games.md`): taxonomy dictionaries `Publisher`/`Category`/`Mechanic`/`Author` (#114) + `TaxonomyAdminController` (#115) + the `Game` entity with moderation workflow (#116) + the user side of submissions (#117): `GameController` (`/api/v1/games/**`) backed by `GameSubmissionService`, and a read-only `TaxonomyController` (`/api/v1/taxonomy/**`, any authenticated user — the id source for the submission form). Moderator decisions (#118): `GameModerationController` (`/api/v1/moderation/games/**`, MODERATOR/ADMIN) backed by `GameModerationService`, plus content-moderation audit in `game/event/` + `game/service/ContentModerationAuditService`. Expansions (#120) live in the **same `game/` package** (not a separate top-level module — they depend on `Game`, the taxonomy and the whole content-audit infrastructure), prefixed `GameExpansion*`: `GameExpansionController` (`/api/v1/expansions/**`) + `GameExpansionModerationController` (`/api/v1/moderation/expansions/**`). Full-text search (#122) is the subpackage `game/search/` — same reasoning as expansions: it indexes nothing but `game/` content; since #131 it also holds the taxonomy-autocomplete index behind `TaxonomyController`'s two `/suggest` endpoints. Same `model/`/`repository/`/`service/`/`mapper/`/`dto/`/`controller/`/`event/` split as `user/`.
- `collection/` — private per-user collection (#121). **A new top-level module, deliberately *not* inside `game/`** (unlike expansions in #120): it has no moderation workflow, no audit, no taxonomy — it only reads `Game`/`GameExpansion` and the viewer's identity. The dependency runs one way only (`collection` → `game`/`user`); nothing in `game/` knows collections exist. `CollectionController` (`/api/v1/collection/**`, any authenticated user) + `CollectionService`, plus `CollectionCleanupService`/`collection/event` for user-deletion cleanup. Same `model/`/`repository/`/`service/`/`mapper/`/`dto/`/`controller/`/`event/` split as `user/`.
- `common/` — `persistence/` (entity base hierarchy: generic `AbstractEntity<ID>` with auditing timestamps via `@PrePersist`/`@PreUpdate` and JPA-correct equals/hashCode by id; `LongEntity` = `@Id Long` IDENTITY, `UuidEntity` = `@Id UUID` via `@UuidGenerator(style = VERSION_7)`, `ModeratedLongEntity` = `LongEntity` + moderation-workflow fields, see "Games & moderation workflow"), `domain/` value objects, email service, logging (`LoggingAspect` wraps every `@RestController` for `Handled request:` lines + `CorrelationIdFilter` for MDC), and the exception infrastructure.
- `config/DevDataInitializer` — seeds two users (`john.doe@example.com` admin, `jane.smith@example.com` user, password `password123`) **only under `dev` profile**. Tests rely on the same IDs/emails via `data.sql`.

### Security & JWT pipeline
- `SecurityConfig` is stateless (`SessionCreationPolicy.STATELESS`), CSRF disabled, only `/h2-console/**`, `/api/v1/auth/**`, `/swagger-ui/**`, `/v3/api-docs/**` are `permitAll`.
- Custom `authenticationEntryPoint` returns **HTTP 401** (not Spring's default 403) with body `{"errorCode":"ACCESS_DENIED","message":"Authentication required"}`. Tests for unauthenticated requests must expect `isUnauthorized()`.
- `JwtAuthFilter` runs before `UsernamePasswordAuthenticationFilter`, **but `shouldNotFilter` skips `/api/v1/auth/{login,register,refresh}`** — those endpoints never touch the JWT filter.
- **`AuthServiceImpl.login` is enumeration-safe**: unknown e-mail and wrong password return the **same** `INVALID_CREDENTIALS` (401) — never `EMAIL_NOT_FOUND` (404). The password is verified **first and always**; for an unknown e-mail a `passwordEncoder.matches(...)` against a `@PostConstruct`-generated dummy bcrypt hash runs anyway, so response time is constant (no timing oracle). `USER_NOT_ACTIVATED` (403) is thrown **only after a correct password** — so account state leaks to the credential owner only, never to an unauthenticated prober.
- Four token types (`JwtTokenType`): `ACCESS` (15 min), `REFRESH` (7 days, cookie-only, scoped to `/api/v1/auth/refresh`), `ACTIVATION` (24 h), `PASSWORD_RESET` (15 min). Each has its own HS256 secret in `application*.yml` under `jwt.*.secret`.
- Refresh tokens are stored in Redis (`RedisRefreshTokenStore`) with a per-user cap (`maxActiveTokensPerUser: 5`). Used activation/password-reset/access tokens are blacklisted in Redis by JTI (`TokenBlacklistService`). Logout blacklists the access token AND calls `jwtService.revokeUsersTokens(email)` to invalidate every refresh.
- **Immediate token invalidation on deactivate / delete / password-change** (GH-63): `UserServiceImpl` (deactivate/delete/`deleteByEmail`) and `AuthServiceImpl.confirmPasswordReset` publish domain events in `user/event/`, handled by `UserSecurityEventListener` with `@TransactionalEventListener(AFTER_COMMIT)` — side effects fire only if the DB change actually commits. The listener revokes refresh tokens (`RedisRefreshTokenStore.revokeAllByUserEmail`), sets a **session epoch** (`RedisSessionEpochStore`, Redis key `token_invalid_after:{email}`, TTL = ACCESS validity), and evicts the auth-state cache. `UserReactivatedEvent` / `UserRolesUpdatedEvent` only evict the cache — they do **not** clear the epoch, so reactivation never resurrects old tokens (re-login required).
- `JwtAuthFilter` loads `{enabled, authorities, invalidAfter}` via `UserAuthStateProvider` (cached, see below) and itself writes the `ApiError` 401 body for two cases: disabled user → **`ACCOUNT_DISABLED`**, access token whose `iat` predates the epoch → **`TOKEN_REVOKED`**. The blacklist branch and every other invalid-token case instead fall through to the entry point's generic `ACCESS_DENIED`. The authenticated principal is the **email String** (downstream only uses `authentication.getName()`), not a `UserDetails`.
- Per-request user state is cached in-memory via Caffeine (`userAuthState`, 60 s TTL, `CacheConfig`) — the TTL is only a safety net; every mutation evicts the entry immediately. Caffeine is per-instance: under horizontal scaling staleness is bounded by the TTL (full consistency would need a Redis-backed cache / pub-sub eviction).

### Audit log
- **Persistent audit of account mutations** (who/whom/what/when): `UserServiceImpl` (`updateUserRoles` → `ROLE_CHANGE`, plus `DEACTIVATE` / `ACTIVATE` / `DELETE` / `FORCE_LOGOUT`) and `AuthServiceImpl.confirmPasswordReset` (`PASSWORD_CHANGE`, self-service so `actor == target`) publish a **dedicated `UserAuditEvent`** — separate from the GH-63 security events, so `UserSecurityEventListener` stays untouched. `activateUser` takes a `requesterEmail` purely to record the actor (no new guard).
- `AuditLogEventListener` (`@TransactionalEventListener(AFTER_COMMIT)`) delegates to `AuditLogService.record`, which is **`@Transactional(REQUIRES_NEW)`** — a new tx is mandatory because AFTER_COMMIT runs after the business tx already committed/closed, and it must be a **separate bean** (self-invocation would bypass the proxy). Consequence: an audit-write failure does **not** roll back the business action (logging never blocks it); a rolled-back action never delivers the event → no entry (so "exactly one entry per committed action").
- `UserAuditLogEntry` (`LongEntity`, table `user_audit_log`, migration `V4`) has **no FK to `application_users`** — entries must survive a user `DELETE`, so `targetId` / `targetEmail` / `actor` are copied values, not relations. `created_at` (from `AbstractEntity`) is the "when". `details` is nullable `text` — only `ROLE_CHANGE` fills it, with before/after role names as small hand-built JSON (roles are a controlled `ROLE_*` vocabulary, no escaping needed). `correlationId` is snapshotted from MDC (`CorrelationIdFilter.CORRELATION_ID`) at publish time to link the entry to request logs. Entity + `AuditAction` enum live in `user/model` (coverage-excluded); service in `user/service`, event + listener in `user/event`.

### Games & moderation workflow (GH-116 data layer + GH-117 user submissions + GH-118 moderation decisions & content audit + GH-119 read library & moderator edit/delete + GH-120 expansions)
- **One entity with a status, not separate "submission"/"game"** (roadmap decision): the global library is `moderationStatus = APPROVED`, "my submissions" is `submittedBy = me AND status IN (DRAFT, PENDING, REJECTED)`. No copy step on approval.
- `ModeratedLongEntity` (`@MappedSuperclass extends LongEntity`) + `ModerationStatus` enum live in **`common/persistence`** — not `game/model`, because `common` must not depend on `game`, and #120 (`GameExpansion`) reuses the same base. Workflow fields: `moderationStatus`, `submittedBy` (UUID, `updatable = false`), `reviewedBy`/`reviewedAt`/`rejectionReason` (nullable), `resubmissionCount`. The protected constructor `(UUID submittedBy, ModerationStatus initialStatus)` is the single place defining a fresh submission: `submittedBy` is null-checked, `initialStatus` is restricted to `DRAFT`/`PENDING` (`IllegalArgumentException` otherwise — a programming-error guard, not an `ErrorCode`), count 0. `Game.builder()` defaults to `PENDING` when `moderationStatus` is omitted. User-side transitions (GH-117) live on the base class: `submitForModeration()` (DRAFT→PENDING) and `resubmit()` (REJECTED→PENDING, `resubmissionCount++`, **clears `reviewedBy`/`reviewedAt`/`rejectionReason`** so a PENDING game never shows a stale rejection reason). Moderator-side transitions (GH-118) also live on the base class: `approve(UUID reviewedBy)` (→APPROVED + `reviewedBy`/`reviewedAt=now`), `reject(String reason, UUID reviewedBy)` (→REJECTED + `rejectionReason`/`reviewedBy`/`reviewedAt`), and `unlockForResubmission()` (REJECTED→DRAFT, **resets `resubmissionCount=0`** and clears all review fields — the moderator override for a submission that hit the resubmission limit). Status guards (who may call them, when) stay in the services because they map to `ErrorCode`s. APPROVED is now reachable through `GameModerationService.approve` (no longer only via SQL fixtures).
- `submittedBy`/`reviewedBy` are **plain UUIDs, no FK to `application_users`** (same rationale as `user_audit_log`/V4: submissions survive a user `DELETE`).
- `Game` (`game/model`, table `games`, migration `V8`) has four `@ManyToMany` sets (LAZY, **no cascade** — dictionaries have independent lifecycles) through singular-named join tables `game_publisher`/`game_category`/`game_mechanic`/`game_author` with composite PKs. Construction via **Lombok `@Builder` on the private constructor** (deliberate new pattern: 9 positional params incl. 5 consecutive ints; a *class-level* `@Builder` would not see the inherited `submittedBy`); collections are populated via `addPublisher/addCategory/...`; `updateDetails(...)` + `clearAssociations()` (GH-117) support PUT — an edit replaces all four collections wholesale (`clear()` on the managed sets, never a reference swap). "≥1 publisher/category" and `min <= max` are **deliberately not enforced** in entity or DB — `GameContentWriter.validateDomainRules` (GH-119: extracted from `GameSubmissionServiceImpl` into a shared `@Component` so the moderator-edit path reuses identical rules + association-building) enforces them in a fixed order: `INVALID_PLAYER_COUNT` → `PUBLISHER_REQUIRED` (union of `publisherIds` + `newPublisherNames`) → `CATEGORY_REQUIRED` (tests assert specific codes under multiple simultaneous violations). `GameContentWriter.applyAssociations` holds the in-flight dictionary find-or-create; both `GameSubmissionServiceImpl` and `GameModerationServiceImpl` delegate to it.
- V8 join tables: `ON DELETE CASCADE` on the `game_id` side only; the dictionary side is RESTRICT (plus dictionary-side indexes `idx_game_*_*_id` — Postgres doesn't auto-index FK columns) — handled since GH-117: `TaxonomyServiceImpl.delete*` throws the `*_IN_USE` codes (409) via `GameRepository.existsBy{Publishers,Categories,Mechanics,Authors}Id` before deleting; the DB-side RESTRICT stays as a second line of defense. Fixture consequence: **all three seeded publishers are game-referenced**, so taxonomy delete-tests must target unreferenced entries (category 3, author 2) or freshly created ones.
- **H2 caveat**: tests run on the Hibernate-generated schema, so V8's `ON DELETE CASCADE`, indexes (`idx_games_moderation_status`, `idx_games_submitted_by`) and column DEFAULTs don't exist there — `GameRepositoryTest`'s delete test verifies JPA-level join-row cleanup (Game owns the ManyToMany), NOT the SQL cascade; validating V8/V11 themselves requires booting the dev profile (done 2026-08-06 on PostgreSQL 16.13: all 11 migrations applied from scratch, and `DELETE FROM games` on a game with an expansion was rejected by `game_expansions_base_game_id_fkey` — confirming the RESTRICT second line of defense behind `GAME_HAS_EXPANSIONS`). Fixture consequence: `data.sql` games must set `resubmission_count` explicitly, and `created_at` of seeded rows is NULL (assert it only on rows persisted through JPA).
- `GameMapper` follows `UserMapper`'s `uses = {...}` pattern (delegates collection elements to the #114 mappers; MapStruct converts `Set<Entity> → List<Dto>` automatically). `GameDto` exposes `moderationStatus` + `rejectionReason` but **not** `submittedBy`/`reviewedBy`/`reviewedAt`/`resubmissionCount` (moderation-internal); GH-118 adds the moderator view `GameModerationDto` (via `GameMapper.toModerationDto`) which **does** expose those four fields. Moderation endpoints return `GameModerationDto`, user endpoints keep returning `GameDto`. Mapping touches all four LAZY collections — solved in GH-117 with `hibernate.default_batch_fetch_size: 20` in `application.yml` (a four-collection `@EntityGraph` would be a cartesian product: rows = publishers × categories × mechanics × authors per game; an `@EntityGraph` is fine for at most one collection). List order is nondeterministic (`HashSet` source).
- `GameRepository` shapes anticipate the known query patterns: `findByTitle` returns `List` (title is deliberately **not unique** — the moderation model keeps rejected duplicates alongside approved originals, so an `Optional` finder would throw on the first duplicate), `findByModerationStatus` is `Page`-only (for APPROVED it's the entire global library). GH-117 adds `findBySubmittedByAndModerationStatusIn` (`Page`, backs "my submissions") and the four `existsBy*Id` queries behind the `*_IN_USE` guards.
- **GH-117 endpoints** (`GameController`, any authenticated user — no role check): `POST /api/v1/games` (body flag `submit`: true = PENDING, false/absent = DRAFT), `GET /api/v1/games/my` (paginated own DRAFT/PENDING/REJECTED; **path is `/my`, not `/mine` as the issue text says**; `@PageableDefault(sort = "id", DESC)` — NOT `createdAt`, which is NULL on H2-seeded rows), `GET /{id}` (GH-119 **unified**: served by `GameLibraryService.findGame` — returns the game if APPROVED **or** you own it in any status; else `GAME_NOT_FOUND`), `PUT /{id}` (own DRAFT/REJECTED only, otherwise `GAME_NOT_EDITABLE` 409; the `submit` field is ignored on PUT), `POST /{id}/submit` (DRAFT/REJECTED → PENDING; over the limit → `RESUBMISSION_LIMIT_EXCEEDED` 409 with status and counter untouched). **Enumeration-safe 404**: someone else's non-APPROVED game throws the same `GAME_NOT_FOUND` as a missing one (no `NOT_GAME_OWNER` code) — same philosophy as login.
- **GH-118 endpoints** (`GameModerationController`, `@PreAuthorize("hasAnyRole('MODERATOR','ADMIN')")` — USER → 403, anon → 401): `GET /api/v1/moderation/games` (paginated PENDING queue, reuses `GameRepository.findByModerationStatus(PENDING, …)`; `@PageableDefault(sort = "id", DESC)`), `POST /{id}/approve` (PENDING→APPROVED + cascade taxonomy approve), `POST /{id}/reject` with body `{reason}` (PENDING→REJECTED; blank reason → `REJECTION_REASON_REQUIRED` 400, **checked before the game lookup** — input-first, not enumeration-safe here, unlike the user side), `POST /{id}/unlock` (REJECTED→DRAFT). Acting on a game in the wrong status → `GAME_NOT_PENDING` (approve/reject) or `GAME_NOT_REJECTED` (unlock), both 409. New `ErrorCode`s (all Domain/INFO, deviating from the issue's Application-section suggestion for symmetry with the existing `GAME_NOT_EDITABLE` state-guard): `GAME_NOT_PENDING` (409), `GAME_NOT_REJECTED` (409), `REJECTION_REASON_REQUIRED` (400). `GameModerationService` returns DTOs (same LAZY-collection rationale as `GameSubmissionService`); moderator identity resolved via `UserService.findUserIdByEmail(new Email(authentication.getName()))`.
- **GH-119 read library** (`GameController`, any authenticated user): `GET /api/v1/games` — the global library, **APPROVED-only**, paginated (`@PageableDefault(sort = "id", DESC)`) with optional filters bound as individual `@RequestParam`s into a `GameLibraryFilter` record (`publisherId`/`categoryId`/`mechanicId` = equality over the M:N join, `players` = `minPlayers ≤ N ≤ maxPlayers`, `maxPlayingTime` = `≤`, `yearPublished` = exact, `age` = `minAge ≤ N`; all optional). Backed by `GameLibraryService.findLibrary` → `GameRepository.findAll(GameSpecifications.library(filter), pageable)`. **Filtering uses `JpaSpecificationExecutor<Game>`** (first game-module use): `GameSpecifications` composes optional predicates via `Specification.allOf` (null predicate = omitted) and always pins `moderationStatus = APPROVED`; the "omit-when-null" idiom (`equalsIfPresent` / `lessThanOrEqualToIfPresent` / `greaterThanOrEqualToIfPresent`) lives once in the shared `common/persistence/Specifications` util, reused by both `GameSpecifications` and `UserAuditLogSpecifications` (GH-89) — since GH-120 that util also owns `joinEqualsIfPresent` (M:N join + `query.distinct(true)` so an INNER JOIN on a collection doesn't multiply rows — it was private in `GameSpecifications` until expansions needed the identical predicate), leaving `supportsPlayers` (two-sided `min ≤ N ≤ max`) as the only genuinely game-specific one. `GameLibraryService.findGame` also backs the unified `GET /{id}` above (moved/generalized from the removed `GameSubmissionService.findMySubmission`); it **short-circuits APPROVED** (returns immediately, no owner lookup) and only resolves the viewer's id to check ownership for non-APPROVED games.
- **GH-119 moderator edit/delete** (`GameModerationController`, MODERATOR/ADMIN — deliberately **not** the issue's literal `/api/v1/games/{id}`, which would clash with the owner-side `GET`/`PUT` on `GameController`): `PUT /api/v1/moderation/games/{id}` (`GameModerationService.updateApprovedGame`) edits an **APPROVED** game only — guard → `GAME_NOT_APPROVED` (new Domain `ErrorCode`, 409, symmetric with `GAME_NOT_PENDING`/`GAME_NOT_REJECTED`); re-validates via `GameContentWriter`, replaces all four collections, then calls `approvePendingTaxonomy(game)` so any in-flight new publisher/author is approved immediately (a library game must never reference PENDING taxonomy); audit `EDIT`. `DELETE /api/v1/moderation/games/{id}` (`GameModerationService.deleteGame`) is a **hard-delete** that works on **any status except DRAFT** (decision "variant C"; a private DRAFT is invisible to the moderator → `GAME_NOT_FOUND`, enumeration-safe — reusing `GAME_NOT_FOUND`, no new code); `gameRepository.delete(game)` cascades the M:N join rows (Game is the owning side; the dictionaries survive). Audit `DELETE` carries the **deleted title in `details`** (targetId is dead after a no-FK hard-delete, so the title is the only forensic trace). Returns 204. Since GH-120 the delete is **blocked when the game has expansions** → `GAME_HAS_EXPANSIONS` (409). The `OpenApiDocumentationTest` smoke test asserts the `/api/v1/moderation/games/{id}` path exists.
- **Content-moderation audit** (GH-118, mirrors `UserAuditLog` GH-64/#89 exactly): `ContentModerationAuditLog` (`LongEntity`, table `content_moderation_audit_log`, migration **V10**, **no FK to `games`** so entries survive #119 hard-delete), enums `ContentModerationAction` (`SUBMIT, RESUBMIT, EDIT, APPROVE, REJECT, UNLOCK, DELETE` — `DELETE` now emitted by GH-119 hard-delete) + `ContentModerationTargetType` (`GAME, EXPANSION` — `EXPANSION` in use since GH-120). `ContentModerationAuditEvent` is published inside the services; `ContentModerationAuditListener` (`@TransactionalEventListener(AFTER_COMMIT)`) delegates to `ContentModerationAuditService.record` which is a **separate bean** `@Transactional(REQUIRES_NEW)` (same "exactly one entry per committed action; rolled-back action → no entry; audit-write failure never blocks the business action" contract as the user audit). `correlationId` snapshotted from MDC (`CorrelationIdFilter.CORRELATION_ID`). **Both `GameModerationServiceImpl` (APPROVE/REJECT/UNLOCK, plus GH-119 EDIT on approved-edit & DELETE on hard-delete; actor = moderator) and `GameSubmissionServiceImpl` (SUBMIT on create-with-submit & DRAFT→PENDING, RESUBMIT on REJECTED→PENDING, EDIT on PUT; actor = submitter) publish these events** — GH-118 back-filled the #117 submission paths so the audit covers the whole lifecycle. GH-120 adds the expansion services on the same terms, and factors the previously-duplicated `publishAudit`/MDC-snapshot into `game/service/ContentModerationAuditPublisher` (one `@Component`, four callers). A DRAFT-only create emits nothing (not a moderation event). `details` carries the rejection reason for REJECT and the deleted title/name for DELETE (the only forensic trace after a no-FK hard-delete), null otherwise. **Games and expansions share the audit table but have independent id sequences**, so `findByTargetId` alone can mix them up — expansion-side code and tests use `findByTargetTypeAndTargetId`. `V10` adds indexes `idx_cma_target_id`/`idx_cma_actor`/`idx_cma_action`; H2/test runs on the Hibernate schema (Flyway off) as usual. No admin read endpoint for the moderation log yet (out of #118 scope, analogous to #89).
- **GH-120 expansions — the override model.** `GameExpansion` (`game/model`, table `game_expansions`, migration **V11**) extends the same `ModeratedLongEntity`, so the whole workflow (statuses, resubmission limit, audit) is identical to `Game`. What differs: `baseGame` is a `@ManyToOne(LAZY, optional = false)` with `updatable = false` (**PUT cannot move an expansion to another game** — changing the base changes every inherited value, that's a new submission), and the four overridable fields (`minPlayers`/`maxPlayers`/`playingTimeMinutes`/`minAge`) are **`Integer`, not `int`** — `null` carries the meaning "inherit from the base game", as do the two empty `@ManyToMany` sets (`expansion_category`/`expansion_mechanic`). Inheritance logic lives in the entity as `getEffective*()` getters (MapStruct picks them up by name into the DTO's `effective*` components), so it is one source of truth for the mapper, validation and future Meili indexing. Scope is deliberately the issue's literal field list: **no `yearPublished`, no `coverImageUrl`** on an expansion. `GameExpansionDto` exposes own **and** effective values side by side so the front can tell an override from an inheritance without fetching the base game; `GameExpansionModerationDto` adds the four moderation fields, exactly like `GameDto`/`GameModerationDto`.
- **GH-120 endpoints.** User side (`GameExpansionController`, any authenticated user): `POST /api/v1/expansions` (body flag `submit`), `GET /my`, `PUT /{id}` (own DRAFT/REJECTED), `POST /{id}/submit`, plus the read side `GET /api/v1/expansions` (APPROVED-only library) and `GET /{id}` (unified: APPROVED **or** own in any status, else `EXPANSION_NOT_FOUND` — enumeration-safe, same philosophy as games). Moderator side (`GameExpansionModerationController`, MODERATOR/ADMIN): `GET`, `POST /{id}/{approve,reject,unlock}`, `PUT /{id}` (APPROVED only), `DELETE /{id}` (hard-delete, any status except DRAFT). Library filters are **`baseGameId` + `categoryId` + `mechanicId` only**, and the taxonomy ones match the expansion's **own** collections — filtering on effective values would need `COALESCE(expansion, baseGame)` in the Criteria API and is deliberately deferred to Meilisearch (#122); `GameExpansionSpecifications` keeps only `hasBaseGame` local (a `@ManyToOne`, so no join and no `distinct`).
- **GH-120 `baseGame` must be APPROVED** — checked on create, PUT, `POST /{id}/submit` (a draft can sit for weeks while the base game changes status) **and again at approve** (defensive: APPROVED is effectively terminal today, but it costs one `SELECT` per moderator action). `min ≤ max` is validated on the **effective** pair, so an own `minPlayers` above an *inherited* `maxPlayers` is rejected too. New `ErrorCode`s: Domain `BASE_GAME_NOT_APPROVED`, `EXPANSION_NOT_{APPROVED,EDITABLE,PENDING,REJECTED}`, `GAME_HAS_EXPANSIONS` (all 409) + `BASE_GAME_REQUIRED` (400) + Application `EXPANSION_NOT_FOUND` (404) — mirroring the `GAME_*` codes rather than reusing them, so an `ApiError` on `/expansions/**` never claims "Game is not pending moderation". `RESUBMISSION_LIMIT_EXCEEDED` / `INVALID_PLAYER_COUNT` / `REJECTION_REASON_REQUIRED` / `CATEGORY_NOT_FOUND` / `MECHANIC_NOT_FOUND` are reused as-is, and an unknown `baseGameId` is a plain `GAME_NOT_FOUND`. **`baseGameId` is deliberately not `@NotNull`** in `GameExpansionRequestDto`: both PUTs ignore it (`baseGame` is `updatable = false`), so Bean Validation would reject an edit over a field the edit never reads — `createExpansion` checks it explicitly instead and throws `BASE_GAME_REQUIRED`, the same Domain/400 shape as `PUBLISHER_REQUIRED`/`CATEGORY_REQUIRED`. **Known, accepted asymmetry:** `POST /api/v1/expansions` answers `BASE_GAME_NOT_APPROVED` (409) for a game that exists but isn't APPROVED, so it *does* leak the existence of someone else's private DRAFT — unlike the enumeration-safe `GET /api/v1/games/{id}`, which returns `GAME_NOT_FOUND` there. This is what #120's acceptance criterion asks for literally; the leak is id-existence only, no content or owner.
- **GH-120 deliberate asymmetries vs. the game services.** Approving an expansion does **not** cascade-approve taxonomy (an expansion has no publishers or authors of its own, and categories/mechanics are curated → always APPROVED), and `GameExpansionContentWriter` creates **nothing in flight** — it only resolves ids. Deleting a **game** that has expansions is **blocked** (`GAME_HAS_EXPANSIONS`, 409) instead of cascading: the FK `game_expansions.base_game_id` is deliberately left at `RESTRICT` in V11, and the service guard counts expansions in **every** status (the FK would block regardless, so a narrower guard would surface as an unhelpful `DATA_CONFLICT`). Same "guard in the service + RESTRICT as second line of defense" shape as the taxonomy `*_IN_USE` checks. Shared plumbing extracted in GH-120: `ContentModerationAuditPublisher`, the `TaxonomyResolver` bean (`resolveCategories`/`resolveMechanics`) and the `common/persistence/RepositoryLookups` util (`findAllOrThrow` + `nullSafe`, previously private inside `GameContentWriter`) — the bean and the statics are deliberately separate classes so `TaxonomyResolver` stays a plain injectable collaborator.
- `GameSubmissionService` **returns DTOs, not entities** (deliberate deviation from `TaxonomyService`): `Game` has four LAZY collections, so mapping happens inside the `@Transactional` service instead of relying on OSIV. Identity: the controller passes `new Email(authentication.getName())`, the service resolves the UUID via `UserService.findUserByEmail`.
- **Resubmission limit**: `gamehive.moderation.max-resubmissions` (`ModerationProperties`, `game/config`) — default **5** in `application.yml`, **2** in `application-test.yml`; fixture game 6 has `resubmission_count = 2`, i.e. exactly at the test limit.
- **In-flight dictionary creation** on submission: `newPublisherNames` → find-or-create by trimmed name (new = `Publisher` PENDING; existing name = reuse regardless of status — a plain create would 500 on the UNIQUE constraint); `newAuthors` → find-or-create by trimmed first+last pair (new = `Author` PENDING; existing pair = reuse **without** status change). Categories/mechanics are curated — referenced by id only (all id lists resolved via one `findAllById` batch + distinct-count check → `*_NOT_FOUND`). Losing a concurrent find-or-create race returns 409 `DATA_CONFLICT` (see Error handling), not 500.
- **Authors carry a moderation status since GH-117** (deliberate deviation from the issue text "authors without status"): shared enum `TaxonomyStatus` (renamed from `PublisherStatus`; values unchanged, so DB columns and API params are untouched), column added by `V9__add_status_to_authors.sql` (existing rows backfilled to APPROVED). Admin `createAuthor` → APPROVED; `POST /api/v1/admin/taxonomy/authors/{id}/approve` mirrors the publisher flow (idempotent); both author list endpoints accept `?status=`. GH-118: approving a game **does** cascade-approve its PENDING authors as well as publishers (`GameModerationServiceImpl.approvePendingTaxonomy` flips every non-APPROVED `Publisher`/`Author` on the game in the same transaction).
- Fixture consequences (`data.sql`): games 4–6 belong to Jane (4 DRAFT, 5 REJECTED count=1, 6 REJECTED count=2); game 3 (John's) is the "someone else's submission" case; author 3 (`Oczekujacy Autor`) is the only PENDING author and is game-unreferenced (approve/filter tests rely on both facts). GH-118: game 2 (`Pandemic`) is the **only** PENDING game in `data.sql` and `GameRepositoryTest` asserts `findByModerationStatus(PENDING)` = `containsExactly("Pandemic")` — so moderation tests must **not** add a PENDING game to `data.sql`. The approve-cascade test therefore builds its own PENDING game in-flight (via `POST /api/v1/games` with `newPublisherNames`/`newAuthors`), and the service-level audit tests (`GameModerationServiceAuditTest`, `GameSubmissionAuditTest`) create + clean up their own committed rows (they run non-`@Transactional` so `AFTER_COMMIT` fires; `@AfterEach` deletes the rows + `auditRepository.deleteAll()`). GH-119: **no `data.sql` change** — `Agricola` (game 1, Jane's) is the **only** APPROVED game, which is enough for the library read (`containsExactly("Agricola")`) and match/no-match filter tests; `GameModerationServiceAuditTest.@AfterEach` now guards its cleanup with `existsById` because the DELETE audit test hard-deletes its seeded game. **GH-120 changed `data.sql`**: game 7 `Carcassonne` (John's, APPROVED) is the base of every seeded expansion — it exists precisely so that expansions do *not* hang off `Agricola`, which `GameModerationControllerTest.delete_approved_204` hard-deletes and which would now 409. ### Collections (GH-121)
- **Two separate tables, no polymorphic target** (roadmap decision): `GameCollectionItem` (`game_collection_items`) and `ExpansionCollectionItem` (`expansion_collection_items`), both `LongEntity`, migration **V12**. Each holds `userId` (UUID), a `@ManyToOne` to the target, `ownershipStatus`, and a UNIQUE `(user_id, target_id)`. `createdAt` from `AbstractEntity` is the "when" — no separate column; the DTO exposes it as `addedAt`. `OwnershipStatus` has a single value `OWNED` in MVP (the enum exists so `WISHLIST`/`PLAYED` won't need a column-type migration). There is **no request body** on any endpoint — with one status there is nothing to send.
- **`userId` is a plain UUID with no FK to `application_users`** (same convention as `submittedBy` / `user_audit_log`). Consequence: the DB won't clean up after a deleted account, so `CollectionUserCleanupListener` (`collection/event`, `@TransactionalEventListener(AFTER_COMMIT)`) does — delegating to `CollectionCleanupService.removeAllForUser`, a **separate bean** `@Transactional(REQUIRES_NEW)` (same rationale as the audit services: the business tx is already closed, and self-invocation would bypass the proxy). This is why **`UserDeletedEvent` carries `(email, userId)`** since GH-121 — AFTER_COMMIT the user row is gone, so the id can no longer be looked up by e-mail. `UserSecurityEventListener` only reads `email()` and was untouched. Contract as with the audit: rolled-back account delete → no event → collection intact; a failing cleanup does **not** roll back the account delete. Both `deleteByUserId` finders are **`@Modifying @Query` bulk deletes, not derived deletes** — a derived `deleteByUserId` loads every entity and emits one `DELETE` per row, which for a large collection means hundreds of statements inside the `REQUIRES_NEW` tx. The bulk form bypasses the persistence context, which is harmless here: the only callers are the AFTER_COMMIT listener (fresh tx, holds no collection entities) and test `@AfterEach` cleanup.
- **Hard-delete of a game/expansion cascades to collection items via the DB.** The FK carries `ON DELETE CASCADE` in V12 **and** `@OnDelete(action = OnDeleteAction.CASCADE)` on the `@ManyToOne` — the annotation makes Hibernate emit `on delete cascade` into the **generated H2 schema too**, so this is the one place where a migration-level cascade is actually exercised by the test suite (see the H2 caveat under "Games & moderation workflow"). Deliberate consequence: `game/` needs no cleanup code, and the existing tests that hard-delete game 1 / expansion 1 (`GameRepositoryTest`, `GameModerationControllerTest`, `GameExpansionModerationControllerTest`) now implicitly prove the cascade, since the fixtures point collection entries at exactly those targets. Deleting a **game with expansions** stays blocked by `GAME_HAS_EXPANSIONS` (#120), so an expansion's collection entry is never silently cascaded away through its base game.
- **Endpoints** (`CollectionController`, any authenticated user, identity from the token only — no path/param ever carries a `userId`): `POST`/`DELETE` `/api/v1/collection/games/{gameId}` (201 / 204), `GET /api/v1/collection/games` (paginated, `@PageableDefault(sort = "id", DESC)`), and the mirror trio under `/api/v1/collection/expansions/**`. The list DTOs nest the **full target DTO** (`GameDto` / `GameExpansionDto` via `CollectionMapper` with `uses = {GameMapper, GameExpansionMapper}`), so the front gets effective expansion values without a second call — and, as in `GameSubmissionService`, the service returns DTOs because mapping touches LAZY collections.
- **Only APPROVED targets go into a collection** — including your own DRAFT (the collection is a view over the library, not over submissions). GH-121 **reuses the existing `GAME_NOT_APPROVED` / `EXPANSION_NOT_APPROVED`** (Domain, 409) instead of adding the issue's `TARGET_NOT_APPROVED`: the codes already existed and say which target they mean. Only two new codes: Domain `ALREADY_IN_COLLECTION` (409) and Application `COLLECTION_ITEM_NOT_FOUND` (404). Guard order in `addGame`/`addExpansion` is fixed: lookup → not-approved → duplicate. The service-level duplicate check gives the readable error; the UNIQUE constraint is the second line of defense, so losing a race yields 409 `DATA_CONFLICT` (same shape as the publisher find-or-create race).
- **Known, accepted asymmetry (as in #120):** `POST /api/v1/collection/games/{id}` answers 409 `GAME_NOT_APPROVED` for a game that exists but isn't approved, so it *does* leak the existence of someone else's private DRAFT — unlike the enumeration-safe `GET /api/v1/games/{id}`, which returns `GAME_NOT_FOUND` there. Unlike #120, **no acceptance criterion forces this**; it was chosen for symmetry with the expansion-create path, and because telling an owner "this game does not exist" about their own DRAFT would be actively misleading. The leak is id-existence only, no content or owner.
- **Isolation is structural, not a guard**: every finder is scoped by `userId`, so someone else's entry is indistinguishable from a missing one (`COLLECTION_ITEM_NOT_FOUND`) — enumeration-safe by construction, with no ownership check to forget. An expansion is added **independently of its base game** (no condition on the base game anywhere in `addExpansion`).
- Fixture consequences (`data.sql`): Jane owns game 1 (`Agricola`) and expansion 1 (`Carcassonne: Rzeka`) — chosen precisely because existing tests hard-delete those two; John owns game 7 (`Carcassonne`) as the "someone else's entry" case; **Mark (moderator) must keep an empty collection** — he is the "user with no entries" in tests and the one who adds expansion 1 *without* owning its base game. Jane deliberately does **not** own game 7 even though she owns an expansion of it. `created_at` is set explicitly on these rows (unlike the other fixtures, which leave it NULL) because the DTO exposes `addedAt`.
- Testing notes: `CollectionControllerTest`'s two end-to-end cascade tests need an explicit `em.flush(); em.clear();` after the moderator delete — test and endpoint share one transaction, and Hibernate's auto-flush only covers the query space of the statement being run, so a `SELECT` on `game_collection_items` will *not* flush a pending `DELETE` on `games`. The authoritative cascade tests live in the repository layer (native `COUNT(*)` after an explicit flush). `CollectionUserCleanupTest` runs **non-`@Transactional`** (AFTER_COMMIT must fire) and therefore creates its **own throwaway user** rather than deleting seeded Jane — deleting a seeded user would persist for the whole H2 instance and break other tests; its `@AfterEach` cleanup runs inside a `TransactionTemplate` because `delete(entity)` on a detached entity has no EntityManager outside a transaction.

### Full-text search (GH-122 index & search + GH-132 async/batched indexing & reindex lock + GH-131 taxonomy autocomplete)

Meilisearch integration lives in `game/search/` (`config/`, `controller/`, `dto/`, `event/`, `service/`) — a subpackage of `game/`, not a top-level module, because it indexes nothing but `game/` content. There are **two indexes sharing one `Client`**: `gamehive_content` (#122, this section) and `gamehive_taxonomy` (#131, its own subsection below). All Meili plumbing common to both — SDK calls, exception→`ErrorCode` mapping, task awaiting, batched paging — lives in **`MeiliIndexGateway`**, a plain class (not a bean) instantiated **once per index** in `MeiliClientConfig` (`CONTENT_GATEWAY` / `TAXONOMY_GATEWAY` constants, injected by `@Qualifier`), because the two differ only by `uid`. Consequence for tests: task-outcome ERROR/WARN lines are logged by the *gateway*, so a `ListAppender` asserting their content must attach to `MeiliIndexGateway`, not to the service.

`gamehive_content` (uid from `gamehive.search.index-uid`) holds **both** approved games and expansions; document ids are prefixed (`game-7` / `expansion-1`) because the two tables have independent sequences and Meili restricts docids to `[a-zA-Z0-9_-]` (**no colon**). Documents carry only searchable + filterable fields — responses are hydrated from the DB by `SearchResultHydrator`, so the index can never serve stale content, and expansion documents carry **effective** values (`getEffective*()`), which is what #120 deferred here.

- **Endpoints.** `GET /api/v1/games/search` (`GameSearchController`, any authenticated user): `q` searches `title`/`description`/`baseGameTitle`; filters are individual `@RequestParam`s bound into `GameSearchFilter` — `targetType`, `publisherId`, `categoryId`, `mechanicId`, `authorId`, `baseGameId`, `players`, `maxPlayingTime`, `yearPublished`, `age`, with the **same semantics as the #119 library filters**. Deliberately mapped as a **literal `@RequestMapping("/api/v1/games/search")` in its own controller**, so it neither shares a prefix with `GameController` nor relies on Spring preferring a literal segment over `/{id}` (a test pins that `GET /games/7` still resolves). `@PageableDefault(size = 20)` **without `sort`** — the order is relevance ranking, so `Pageable.getSort()` is ignored; the response is `Page<SearchResultDto>` documented via `PageSearchResultDto`. `POST /api/v1/admin/search/reindex` (`SearchAdminController`, `@PreAuthorize("hasAnyRole('MODERATOR','ADMIN')")`) rebuilds **both** indexes (GH-131) and answers `ReindexResultDto` (`{games, expansions, publishers, authors}`), or **409 `REINDEX_ALREADY_RUNNING`** while another rebuild holds the lock; `SecurityConfig` has no `/api/v1/admin/**` rule, so that annotation is the only thing granting MODERATOR access there. Since GH-132 the controller depends on `SearchReindexService`, **not** on `GameSearchService` — that wrapper is the only caller of `reindexAll()`.
- **One index holding two types forces a wrapper**: `SearchResultDto(targetType, game, expansion)` — exactly one of the two nested DTOs is non-null, and they are the **same `GameDto`/`GameExpansionDto` the library returns**, so the front reuses its cards. Hydration is two batched `findAllById` calls (never N+1) inside `@Transactional(readOnly = true)`, keeping Meili's ranking order and **silently dropping hits whose row is missing or no longer APPROVED** — the index is a hint, the DB is the authority, and a stale document self-heals on the next read.
- **Indexing is event-driven, and the event carries finished documents.** `GameSearchIndexPublisher` (mirroring `ContentModerationAuditPublisher`) builds them via `GameSearchDocumentFactory` **inside the business transaction** and publishes `SearchIndexEvent`; `SearchIndexListener` (`@TransactionalEventListener(AFTER_COMMIT)` **+ `@Async(AsyncConfig.SEARCH_INDEX_EXECUTOR)`**) applies it. The documents must be pre-built because AFTER_COMMIT is too late to touch the LAZY dictionaries or an expansion's base game. Rolled-back decision → no event → index untouched. `SearchIndexEvent` is `(operation, List<GameSearchDocument> documents, String documentId)`: UPSERT carries the list, REMOVE carries a single id (`describeTargets()` renders either for logs).
- **GH-132: the index write runs off the request thread.** `searchIndexExecutor` (`config/AsyncConfig`, `@Profile("!test")`) is **single-threaded on purpose** — the queue is FIFO and one worker drains it, so two events submitted in order are *applied* in order, which a 2-thread pool would not guarantee (note the ordering guarantee starts at submit time: two transactions committing concurrently can still reach `afterCommit` in either order) — with `MdcTaskDecorator` (the MDC snapshot happens at submit time, i.e. still inside the request, before `CorrelationIdFilter` clears it) and a `RejectedExecutionHandler` that **logs ERROR and drops the task** instead of `CallerRunsPolicy`. `setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(30)` are not optional decoration: the default `shutdownNow()` would silently discard the whole queue on every deploy, and the deeper the queue (i.e. the slower Meili is) the more it would lose. That asymmetry with `authEmailExecutor` is the whole point: a full queue must never push Meili back onto the moderator's thread. A dropped task leaves index drift, which a reindex repairs; a blocked moderator cannot be repaired. `TestAsyncConfig` supplies a `SyncTaskExecutor` under `test`, so assertions right after an event stay deterministic without Awaitility. The listener method had to become `public` — `@Async` works through a proxy.
- **SDK timeouts are unreachable through the public API of meilisearch-java 0.21.0**: `CustomOkHttpClient(Config)` does `new OkHttpClient()` (10 s connect/read defaults) and `Config` has no constructor taking an `OkHttpClient`. Against a host that *hangs* rather than refusing connections, a `PUT /api/v1/moderation/games/{id}` with N expansions used to block for minutes and then answer 200. Moving the write off the request thread is therefore the **only** available mitigation; a custom `HttpClient` implementation is deliberately out of GH-132's scope.
- **Only APPROVED is in the index**, so exactly four call sites publish: `approve` and `updateApprovedGame`/`updateApprovedExpansion` → UPSERT, `deleteGame`/`deleteExpansion` → REMOVE, `reject` → REMOVE. The removal on `reject` is **provably a no-op today** (reject only acts on PENDING, so no document exists) — it is kept to hold the invariant if that guard ever loosens; `unlock` publishes nothing at all, and the submission services (`SUBMIT`/`RESUBMIT`/user `EDIT`) are untouched because they only ever touch DRAFT/PENDING/REJECTED.
- **Editing an approved game fans out to its approved expansions — in one batch.** Changing `minPlayers`/`maxPlayers`/`playingTimeMinutes`/`minAge`/categories/mechanics/title on a base game changes the **effective** values of every expansion inheriting them, so `updateApprovedGame` re-upserts them via `GameExpansionRepository.findByBaseGameIdAndModerationStatus(id, APPROVED)`. Since GH-132 that is **one** `publishUpsert(game, expansions)` → one event → one `addDocuments` (`GameSearchService.index` takes a `List`), where #122 emitted `1+N` separate events and `1+N` HTTP calls. The empty-list short-circuit in `index` is pure defence — no production path can reach it, since every publish carries at least the game's own document. Only that one path needs the fan-out: an expansion requires an APPROVED base game at every step, so a PENDING game cannot have approved expansions, and deleting a game with expansions is blocked by `GAME_HAS_EXPANSIONS` (#120) — no orphaned expansion documents.
- **Expansions have no publishers, authors or year** in the #120 model, and `getEffective*()` does not cover them, so those document fields stay empty/null. Consequence to state in the API docs: filtering by `publisherId`, `authorId` or `yearPublished` **matches games only**.
- **Reindex is the repair tool, not the primary path**: `reindexAll()` re-applies settings, `deleteAllDocuments()`, then pages through APPROVED games and expansions via `ApprovedContentDocumentReader` (`@Transactional(readOnly = true)` **per batch** — a document needs a transaction, but holding one across every HTTP call to Meili would not) with `gamehive.search.reindex-batch-size`. The index is briefly empty mid-rebuild; acceptable for an admin operation, and an index swap would be overkill.
- **Concurrent rebuilds are locked out (GH-132).** `SearchReindexService` takes a Redis key `search_reindex_lock` (`setIfAbsent` + TTL `gamehive.search.reindex-lock-ttl`, default 15 min) before delegating, and releases it in `finally` **only when the stored token is still its own**, through a Lua compare-and-delete (`RedisScript`) — a run longer than the TTL may have lost the key to someone else, and a `GET` + `DELETE` pair would leave a window in which the key expires, another instance takes it, and we delete *their* lock. Redis, not an `AtomicBoolean`, because the project assumes horizontal scaling (see the Caffeine note above). Redis unreachable → **fail-open**: ERROR in the log and the rebuild proceeds, since a repair tool must not be blocked by something else already being broken (same instinct as `RedisSessionEpochStore.getEpoch`). Busy → **`REINDEX_ALREADY_RUNNING`**, which lives in the **Application** section of `ErrorCode` (WARN), *not* Domain as GH-132's issue text suggested: a reindex is no domain entity and no business invariant, it is a use-case precondition — do not "fix" it back.
- **`totalElements` is capped by Meili's `pagination.maxTotalHits`, default 1000.** Above that the count plateaus and pages past `1000/size` come back empty even though matching content exists. Not raised in `ensureIndexSettings()` — stated in the endpoint's `@Operation` instead. Raising it means adding a `pagination` setting call there.
- **The compose service uses `${MEILI_MASTER_KEY:?…}`, not a bare substitution**: under `MEILI_ENV=development` Meili does not require a master key, so an empty variable would silently publish an **unauthenticated** search engine on port 7700 while compose only warns in its log — the `:?` form refuses to start instead. (Postgres gets this for free: an empty password makes its container fail on its own.)
- **`MeiliProperties` carries field defaults** (`host`, `indexUid`, `reindexBatchSize = 200`, `reindexLockTtl = 15m`, `taskWaitTimeout = 60s`) because a missing property must not produce an unusable state: batch 0 makes `PageRequest.of(0, 0)` throw, a null uid sends requests to `/indexes/null`, and a null TTL would make `setIfAbsent` throw and turn the reindex lock into a 500. Deliberately **no** `@Validated`/`@NotBlank` — the bean is created regardless of `gamehive.search.enabled`, so validation would break the `test` context, where search is off. There is no `enabled` field either; `@ConditionalOnProperty` is the single reader of that switch.
- **`gamehive.search.enabled` selects the implementation**, via `@ConditionalOnProperty` on both `MeiliGameSearchService` (`matchIfMissing = true`) and `NoOpGameSearchService` (`havingValue = "false"`), plus `MeiliClientConfig`/`MeiliIndexInitializer`. Deliberately a **feature toggle, not `@Profile("!test")`**: it also lets `dev` boot without Meili. `application-test.yml` sets it to `false`, so under `test` no Meili bean exists at all.
- **A green `mvn test` proves nothing about Meilisearch** — the same trap as with Flyway migrations, and for the same reason: the `test` profile runs the fallback, so `MeiliGameSearchService`, `MeiliClientConfig` and `MeiliIndexInitializer` are **never instantiated** by the suite. Its unit tests mock the SDK. Verifying the integration means booting `dev` against a real container. This already bit once: the missing `okhttp-jvm` dependency below compiled and passed all 670 tests, then failed at startup. **The same holds for the GH-132 async path**: under `test` the executor is a `SyncTaskExecutor`, so a green suite says nothing about the real worker thread, MDC propagation into its log lines, or the response actually returning before Meili answers.
- **`okhttp 5` is a Kotlin Multiplatform module**: `com.squareup.okhttp3:okhttp` ships only Gradle metadata and **zero classes**; the JVM classes are in `okhttp-jvm`. Maven cannot read Gradle module metadata, so `meilisearch-java`'s transitive `okhttp` resolves to an empty jar and building the `Client` bean dies with `NoClassDefFoundError: okhttp3/MediaType`. Hence the explicit `com.squareup.okhttp3:okhttp-jvm` (`runtime`) in `pom.xml` — **keep its version equal to the one `meilisearch-java` pulls in** when bumping the SDK.
- **`android-json` shadows `org.json` in test scope.** `spring-boot-starter-test` → `jsonassert` → `com.vaadin.external.google:android-json` occupies the **same `org.json` package** and, unlike the real `org.json:json` (a runtime dependency of the Meili SDK), it does **not** wrap Java arrays into JSON arrays. The SDK builds the search body with `org.json.JSONObject.putOpt`, so on a classpath where `android-json` wins, `SearchRequest.filter(String[])` is serialized as `[Ljava.lang.String;@1929425f` and Meili answers `invalid_search_filter`. The application runtime is fine (no test jars), but **an integration test driving a real Meili instance would silently lose every filter** — exclude `android-json` there. The existing unit tests assert `SearchRequest.getFilter()` (the field), not the serialized body, so they are immune.
- SDK facts worth not rediscovering (verified against 0.21.0): `SearchRequest` has **no setters**, only a Lombok builder; `index.search(SearchRequest)` returns `Searchable`, and the **paginated** mode (`page` + `hitsPerPage`) yields `SearchResultPaginated` with `getTotalHits()`, while `offset`/`limit` yields `SearchResult` with only `estimatedTotalHits` — hence paginated mode, remembering that **Meili pages are 1-based** (`pageable.getPageNumber() + 1`). In hits, `targetType` arrives as `String` and `targetId` as **`Double`** (Gson), so `toHitRefOrNull` casts through `Number` — and a hit that does not parse is **skipped with a warning**, because one malformed document must not turn every search into a 500. Documents are serialized with the SDK's own `GsonJsonHandler` bean (also passed into `Config`, so there is one serializer): Boot 4 ships Jackson **3** (`tools.jackson`) at compile scope, and Gson omits nulls for free. (Jackson **2** is also on the classpath, but it arrives as a transitive of `flyway-core` — it predates this feature and has nothing to do with the search stack. The SDK's own Jackson 2 came via `com.auth0:java-jwt`, which is excluded in `pom.xml`: it only backs `generateTenantToken`, which this project never calls, and the project already has Nimbus JOSE for JWT.)
- **Every Meili operation is an asynchronous task**, and `TaskInfo` only means "enqueued" — a task can still fail afterwards. `reindexAll()` therefore **waits for each task and checks its status** (`waitForTask` + `getTask`; `waitForTask` alone does *not* report failure), counting only `SUCCEEDED` and throwing `SEARCH_FAILED` otherwise. Without that, a rebuild could empty the index, fail on every insert, and answer `200` with full counters — destroying the index in the name of repairing it. **Since GH-132 the event-driven path waits and checks too**: `index`/`delete` call `awaitTaskSucceeded(...)`, which logs ERROR with `taskUid`, the action (carrying the document ids) and the task status, or DEBUG on success — the only trail linking an index drift to the action that caused it. It cannot throw usefully there, since it runs after the commit, so the boolean is ignored on that path and `awaitTaskOrThrow` (reindex only) is the caller that turns `false` into `SEARCH_FAILED`. Blocking on `waitForTask` is acceptable **only because** the listener is no longer on the request thread — that is why the async change had to land first. Note `TaskStatus.toString()` is lower-case (`failed`), which matters when asserting log contents.
- **The no-arg `waitForTask(uid)` hides a 5 s timeout** (`TasksHandler` calls `waitForTask(uid, 5000, 50)`) and reports it as `MeilisearchTimeoutException` — the *same* exception type as an unreachable host. Taken naively that makes a merely slow task indistinguishable from a failed one: the event path would log "index is now out of sync" about a document that was in fact indexed, and a reindex batch would abort after `deleteAllDocuments` had already emptied the index. So the code passes an explicit timeout (`gamehive.search.task-wait-timeout`, default 60 s, poll 50 ms) and `waitUntilSettled` catches `MeilisearchTimeoutException` **separately**, logging WARN "status unknown, it may still complete" instead of ERROR. Timeout is treated as *not confirmed*, so a reindex still aborts rather than reporting counters it cannot vouch for, but the event path stops crying drift.
- **Error bodies carry static messages.** `GlobalExceptionHandler` copies `getMessage()` into `ApiError`, so an interpolated message would reflect the caller's own `q` back at them and leak internals (index uid, document-id scheme). The dynamic action description stays in `log.error` only — same convention as `RedisRefreshTokenStore`.
- **Page size is clamped to 50 in `GameSearchController`**, not globally via `spring.data.web.pageable.max-page-size`: Spring's default cap is 2000, and every hit costs a DB row plus its LAZY collections, but a global cap would silently change the contract of every other paginated endpoint.
- Index failures map to `InfrastructureException`: `SEARCH_INDEX_UNAVAILABLE` (503) for communication/timeout, `SEARCH_FAILED` (500) for any other SDK error. `MeiliIndexInitializer` applies `searchableAttributes` (order = ranking weight: `title`, `description`, `baseGameTitle`) and `filterableAttributes` on `ApplicationReadyEvent`, creating the index if missing and tolerating `index_already_exists`; a failure there is **logged, never fatal** — an unreachable Meili must not block startup.
- `PageImpl` recomputes `totalElements` as `offset + content.size()` on what it considers the last page, so hits dropped during hydration shrink the reported total there. Self-consistent, no code change needed — but do not "fix" the test that pins this.
- **Facets are configured but not returned.** Every filterable attribute is facetable, yet the response stays `Page<SearchResultDto>` for symmetry with the library — a `Page` has nowhere to put a facet distribution. Returning counts means adding a wrapper DTO; deliberately deferred.
- Testing notes: `data.sql` needed **no change** (games 1 + 7 are the only APPROVED ones and expansion 1 is the only APPROVED expansion, which is exactly the "override + inheritance" document case). `GameSearchIndexingTest` runs **non-`@Transactional`** so AFTER_COMMIT fires, and therefore creates and deletes **its own rows** (tracked ids, expansions before games) — mutating seeded games would leak into the whole H2 instance and break the `containsExactly` assertions elsewhere. `MeiliGameSearchServiceTest` mocks `Client`/`Index`/`SearchResultPaginated` but uses the **real** `GsonJsonHandler` and `MeiliFilterBuilder`, so it asserts real JSON and real filter expressions. `SearchFallbackTest` is the only class that does **not** override the `GameSearchService` bean — it proves the fallback is what runs under `test` (and, since GH-132, that `searchIndexExecutor` is the inline `SyncTaskExecutor` there, plus that the reindex lock does not break the fallback path). GH-132 adds `SearchIndexExecutorTest`, which builds the executor straight from `new AsyncConfig()` (the bean is `@Profile("!test")`, so the suite has no other way to see the real pool) and asserts the worker thread, the MDC hand-off, the drop-on-full-queue policy (block the single worker with a latch, submit past `queueCapacity`, assert the caller neither throws nor runs anything) and that `SearchIndexListener.onSearchIndex` still carries `@Async` — an annotation assertion, deliberately, because it is the only deterministic pin for "the moderator does not wait for Meili"; `SearchFallbackTest` completes it with `AopUtils.isAopProxy(searchIndexListener)`, since the annotation is dead without a proxy and the proxy exists even where the executor is inline. `SearchReindexServiceTest` mocks `RedisTemplate` (acquire, 409, fail-open), but the **lock semantics live in `SearchReindexLockIntegrationTest` against embedded Redis** — a mock cannot tell compare-and-delete from a plain `DELETE`, and that difference is the whole point; it covers release after success, release after an exception, and a lock taken over mid-run staying untouched. The end-to-end 409 is in `SearchAdminControllerTest` (`flushAll()` in `setUp` plus an `@AfterEach` that drops the lock key — with a 15-minute TTL it would otherwise leak into classes that do not flush). `MeiliGameSearchServiceTest` is the only class in the project that captures log output (a Logback `ListAppender` on the service's own logger, detached in `@AfterEach`), because the acceptance criterion is about the **content** of the ERROR line; it also documents that a `TaskInfo` mock must be built *before* entering `when(...)`, or Mockito reports `UnfinishedStubbing`.
- Verified end-to-end on `dev` against Meilisearch v1.53 (2026-08-11): boot applies the index settings; a PENDING game is absent from search and appears on approve; searching by a description fragment hits; editing an approved game replaces the document (old term → 0, new → 1); all filter cases behave as specified; deleting a document straight in Meili and then reindexing restores it; hard-delete removes it; USER → 403 and anon → 401 on reindex. - Watch out when driving the API by hand: `submit` is a primitive `boolean`, so Jackson 3 rejects a body that omits it with 400 `VALIDATION_ERROR` — even on `PUT`, which ignores the field's value.

#### Taxonomy autocomplete — the `gamehive_taxonomy` index (GH-131)

Closes the #117 code-review debt: `GET /api/v1/taxonomy/{publishers,authors}` returned the **whole** dictionary, and publishers/authors grow with user submissions (`GameContentWriter` creates them find-or-create at `POST /api/v1/games`), so the submission form would eventually pull thousands of rows on every open. Document: `id` prefixed by type (`publisher-3` / `author-1`), `targetType` (`TaxonomyTargetType`, `game/model`), `targetId`, `name` (for an author the concatenated `"{firstName} {lastName}"`, so one searchable field covers both), `status`. `searchableAttributes = [name]`, `filterableAttributes = [targetType, status]`.

- **A separate index, not a second document shape in `gamehive_content`** — different document shape *and* a different rule for what gets indexed.
- **The rule is the headline difference: `gamehive_content` holds only `APPROVED`, `gamehive_taxonomy` holds EVERY status.** Find-or-create reuses an existing name regardless of status, so hiding a `PENDING` publisher would push the user into typing a duplicate that then dies on the UNIQUE constraint (409 `DATA_CONFLICT`). `status` travels in the DTO so the front can mark an entry "awaiting approval". The `/reindex` `@Operation` states this asymmetry — it is the only place a client can see it.
- **Endpoints** (`TaxonomyController`, any authenticated user): `GET /api/v1/taxonomy/publishers/suggest?q=&limit=` and `.../authors/suggest?q=&limit=`. Flat list of the existing `PublisherDto`/`AuthorDto`, **no `Page`** — autocomplete returns the best `limit` hits, it does not paginate. They live in `TaxonomyController` rather than their own controller because that controller has **no `/{id}` mapping**, so unlike `/games/search` there is nothing to collide with. **`limit` is clamped (`Math.clamp`, 1–50, default 10), deliberately NOT validated with `@Max`**: `GlobalExceptionHandler` has no `ConstraintViolationException` handler, so `@Max` would fall through to the `Exception` fallback and answer **500 instead of 400**. Same instinct as `GameSearchController.clampPageSize`.
- **The fallback is a working implementation, not a no-op** — the sharpest contrast with #122. `DatabaseTaxonomySuggestService` (`@ConditionalOnProperty(havingValue = "false")`) really answers `suggest*` via `JpaSpecificationExecutor`; only `index`/`delete`/`reindexAll` are no-ops, since there is no index to write to. So `gamehive.search.enabled=false` (i.e. the whole test suite, and `dev` without a container) gives **real coverage of this endpoint**, which #122 by definition cannot have. Documented consequence: Meili brings typo-tolerance and relevance ranking, the fallback only `LIKE` + alphabetical sort — **results are not identical**, so tests assert the contract (matches / limit / statuses), never a ranking, and the `@Operation` says the order is not part of the contract.
- **Match semantics live once**, in `TaxonomySpecifications` (`game/service`, next to `GameSpecifications`): publisher by `name`, author by `LOWER(CONCAT(firstName, ' ', lastName))` — one predicate covering first name, last name and the full `"Uwe Rosenberg"` phrase instead of three ORs. The same Specification backs the fallback suggest **and** the admin `?q=` filter, so the two can never drift. `common/persistence/Specifications` gained `likeIgnoreCaseIfPresent` + `likePattern`, which **escapes `%`, `_` and `\`** (with an explicit `ESCAPE` char) — without it `q=%` would match the entire table.
- **No migration.** Nothing in the schema changes. Accepted cost: an unanchored `LOWER(...) LIKE '%q%'` is a seq scan (the UNIQUE btree on `publishers.name` only helps `'q%'`) — fine for a fallback path, since Meili is the primary one; a `pg_trgm` GIN index is deliberately out of scope.
- **Nine publish points**, all via `TaxonomyIndexPublisher` (documents built inside the open transaction, only the immutable record crosses the thread boundary): `TaxonomyServiceImpl` create/approve/delete publisher, create/approve/**rename**/delete author, plus `GameContentWriter.applyAssociations` (in-flight creation) and **`GameModerationServiceImpl.approvePendingTaxonomy`**. That last one is *not* in the issue text and is not optional: the approve cascade flips statuses straight on the entities, bypassing `TaxonomyService`, so without it a suggestion would keep saying `PENDING` after its game was approved. `GameContentWriter` publishes **only freshly created** entries — reusing an existing name does not change the document — and batches publishers + authors into one event (one `addDocuments`, as with the #132 fan-out). `approvePublisher`/`approveAuthor` publish **even when the entry was already APPROVED**: upsert is idempotent, which turns a "pointless" approve into a free index repair.
- **`TaxonomyIndexListener` reuses the existing `SEARCH_INDEX_EXECUTOR`** (`@Async` + `@TransactionalEventListener(AFTER_COMMIT)` + catch-all `RuntimeException`). Deliberately no second executor: the pool is single-threaded, so writes to both indexes stay ordered, and `TestAsyncConfig` needed no change — a new named executor would have to be added there too or the test context would fail to start.
- **Suggestions are hydrated from the DB**, like #122 hits: Meili returns only `targetId`s, `TaxonomySuggestionHydrator` does one batched `findAllById` and rebuilds the DTOs in ranking order. Unlike `SearchResultHydrator` it does **not** filter by status (all statuses are valid here) — it only drops ids whose row is gone.
- **Reindex rebuilds both indexes under the single `search_reindex_lock`** — one repair operation, and a second key would be a second state to forget. Order is content → taxonomy; a failure on content aborts the whole thing and does **not** touch taxonomy, but `finally` still releases the lock. To keep the types honest, `GameSearchService.reindexAll()` now returns `ContentReindexCounts(games, expansions)` and `TaxonomySuggestService.reindexAll()` returns `TaxonomyReindexCounts(publishers, authors)`; the 4-field `ReindexResultDto` is **only** the HTTP body and is assembled in `SearchReindexService`.
- **Legacy list endpoints.** `GET /api/v1/taxonomy/{publishers,authors}` keep their flat-list shape but are **capped at 200** entries and marked `@Deprecated` + `deprecated = true` in OpenAPI, whose description says outright that above the cap this is *not* the complete data and there is no way to fetch the rest. **Decision for the bounded lists: `categories`/`mechanics` stay unpaginated and uncapped** — they are curated, so the full list is fine; `OpenApiDocumentationTest` asserts they are *not* flagged deprecated, so the decision cannot rot silently.
- **Breaking change:** the admin lists `GET /api/v1/admin/taxonomy/{publishers,authors}` now return `Page<...>` (documented via `PagePublisherDto`/`PageAuthorDto`) and accept `?q=` alongside the existing `?status=`, `@PageableDefault(size = 20)` sorted by name / lastName+firstName. `TaxonomyService.find{Publishers,Authors}` changed to `(status, query, Pageable) → Page<...>`; the now-dead `PublisherRepository.findByStatus` / `AuthorRepository.findByStatus` were removed with it.
- Testing notes: **`data.sql` needed no change**, which is worth knowing before "improving" the fixtures — all three seeded publishers contain `"Games"` (so `q=games&limit=2` proves the limit), `Pending Games` is PENDING (the all-statuses case) and the three authors cover first name / last name / full phrase. **Do not add a PENDING author**: `AuthorRepositoryTest` asserts `containsExactly("Autor")`. `TaxonomyIndexingTest` runs **non-`@Transactional`** (AFTER_COMMIT must fire) and therefore creates and deletes **its own** publishers/authors/games, by name in `@AfterEach`. `DatabaseTaxonomySuggestServiceTest` is where the real fallback results are pinned (including wildcard escaping and trimming); `TaxonomySuggestControllerTest` mocks the service to pin parameter binding, clamping and the 400/401/503 shapes; `TaxonomyControllerTest` and `SearchFallbackTest` do **not** mock it, so they assert real end-to-end hits — the pointed contrast being that on the fallback `/games/search` returns an empty page while `/taxonomy/*/suggest` returns real matches. **`MeiliWiringTest` is the only class that boots with `gamehive.search.enabled=true`**: it exists because the rest of the suite runs the fallback, so a typo in a gateway qualifier or a missing bean would otherwise surface only at `dev` startup; it also shows `MeiliIndexInitializer` configuring each index in its own `try` (two independent ERROR lines) without blocking startup.
- **Not yet verified against a real Meilisearch.** The whole `Meili*` path (`MeiliTaxonomySuggestService`, both gateways, index settings, typo-tolerance, actual documents in `gamehive_taxonomy`) is untouched by the suite for the reason stated above, so a green `mvn test` says nothing about it — the same trap as with Flyway migrations. Booting `dev` once against the container is still required.

### Error handling

All thrown errors extend `BaseException(ErrorCode)`. The three subclasses determine **log level only** — HTTP status comes from `ErrorCode.httpStatus` regardless of subclass. Pick the subclass by what kind of failure it is:

- **`DomainException`** — business rule / invariant violated. Logged at INFO.
  Examples: `EMAIL_ALREADY_EXISTS`, `INVALID_PASSWORD`, `CANNOT_REMOVE_LAST_ADMIN`.
- **`ApplicationException`** — use-case flow problem: lookup miss, token validity, precondition not met. Logged at WARN.
  Examples: `USER_NOT_FOUND`, `JWT_EXPIRED`, `JWT_BLACKLISTED`.
- **`InfrastructureException`** — external system or technical layer failed (Redis, SMTP, crypto). Logged at ERROR with stack trace. Always wraps a caught third-party exception.
  Examples: `REDIS_UNAVAILABLE`, `EMAIL_SEND_FAILED`, `JWT_SIGNING_ERROR` (JOSE).

`ErrorCode.java` is grouped into sections (`Domain` / `Application` / `Infrastructure` / `Handler-only`) matching this taxonomy — the section a code lives in tells you which exception class to throw. Adding a new failure mode means: (1) add an `ErrorCode` entry in the matching section with its `HttpStatus`, (2) throw the matching exception subclass. `GlobalExceptionHandler` dispatches by subclass to apply the right log level; the response body (`ApiError(code, message)`) is identical regardless of subclass.

The four "Handler-only" codes (`ACCESS_DENIED`, `DATA_CONFLICT`, `VALIDATION_ERROR`, `INTERNAL_ERROR`) are never thrown directly — they're used by `GlobalExceptionHandler` when wrapping framework exceptions (`AuthorizationDeniedException`, `MethodArgumentNotValidException`, `MethodArgumentTypeMismatchException` → 400 `VALIDATION_ERROR` for malformed path vars such as a bad UUID, `DataIntegrityViolationException` → 409 `DATA_CONFLICT` — the backstop for race conditions: publisher/author find-or-create losing to a concurrent insert on the UNIQUE constraint, or a `*_IN_USE` delete guard losing a TOCTOU race against the FK RESTRICT — and the fallback `Exception`).

### API documentation (OpenAPI/Swagger)
- springdoc-openapi (`springdoc-openapi-starter-webmvc-ui`) generates the spec. Global metadata + the `bearerAuth` security scheme (HTTP/bearer/JWT) live in `config/OpenApiConfig` (`@OpenAPIDefinition` + `@SecurityScheme`); `config` is coverage-excluded. UI at `/swagger-ui.html`, raw doc at `/v3/api-docs` (both already `permitAll` in `SecurityConfig`). **Disabled under `prod`** via `springdoc.api-docs.enabled=false` / `swagger-ui.enabled=false` in `application-prod.yml`.
- Convention: each controller has a `@Tag`; secured controllers carry class-level `@SecurityRequirement(name = "bearerAuth")` (auth endpoints are public, so no requirement). Endpoints use `@Operation` + `@ApiResponses`; error bodies reference `@Schema(implementation = ApiError.class)` (or `ApiValidationError.class` for 400). `AdminUserController` declares the shared 401/403/500 responses **once at class level** (springdoc merges them with method-level ones) — follow that pattern instead of repeating common codes per method.
- Request/response DTOs are documented with `@Schema` on record components (`dto` is coverage-excluded). Auth success bodies use dedicated records `AccessTokenResponseDto` (login/refresh) and `MessageResponseDto` (register/activate) — added so the spec has real schemas instead of raw `Map`/`String`. Note: `register`/`activate` therefore return `application/json`, not `text/plain`. Paginated endpoints document their 200 body with dedicated flat `Page*Dto` records (`PageUserResponseDto`, `PageAuditLogResponseDto`, `PageGameDto`, `PageGameModerationDto`, `PageGameExpansionDto`, `PageGameExpansionModerationDto`, `PageGameCollectionItemDto`, `PageExpansionCollectionItemDto`, `PageSearchResultDto`, `PagePublisherDto`, `PageAuthorDto`) instead of the weak auto-schema for `Page<T>`. - The `OpenApiDocumentationTest` smoke test asserts `/v3/api-docs` returns 200 with the expected title, the `bearerAuth` scheme, and key paths — keep it green when changing OpenAPI config. Since GH-131 it also pins which endpoints are flagged `deprecated`: the growing taxonomy lists yes, the curated `categories`/`mechanics` no.
- **Deprecating an endpoint** = Java `@Deprecated(since = "GH-<issue>")` on the handler **and** `@Operation(deprecated = true, ...)` with a description saying what to use instead and what the caller loses by staying — see the two taxonomy lists. ### Persistence
- Prod: PostgreSQL with **Flyway** (`src/main/resources/db/migration/V*__*.sql`). `ddl-auto: none` — schema changes go through new `V*` files. **Spring Boot 4 split auto-config into per-tech modules — Flyway runs only with the `spring-boot-starter-flyway` dependency; bare `flyway-core` no longer self-configures (migrations silently won't run).**
- **Never edit a `V*` file that has already been applied to a database** — fix forward with a new `V*` instead. Flyway stores a checksum per applied migration and refuses to boot on mismatch (`FlywayValidateException: Migration checksum mismatch`). This bit once already: `d7a981d` ("GH-116 poprawki po CR") appended four `CREATE INDEX` to an already-applied `V8`, which left the dev DB stuck at V8 for five weeks and silently missing those indexes plus V9/V10/V11. Recovery on a dev box is `docker compose down -v` + restart (drops the named volume — `docker compose down` alone keeps it, so the error just repeats); `flyway repair` only rewrites the checksum and would leave the amended statements permanently unapplied.
- **A green `mvn test` proves nothing about migrations.** The `test` profile disables Flyway and lets Hibernate generate the schema, so `V*` files are never executed there — checksum drift, broken DDL, `ON DELETE CASCADE`, indexes and column DEFAULTs are all invisible to the suite. (The one exception is a cascade *also* declared on the entity via `@OnDelete`, as in V12's collection tables — Hibernate then puts it into the H2 schema as well, so the behaviour, though not the migration file, is covered.) Verifying a new migration means booting the `dev` profile once (`mvn spring-boot:run`) against real PostgreSQL.
- Test: H2 in PostgreSQL-compat mode, `ddl-auto: create-drop`, **Flyway disabled**, `data.sql` populates fixtures (`schema-locations: []` is intentional — Hibernate creates the schema, only data.sql runs).
- `AppUser` ↔ `UserRole` is many-to-many through `user_roles` join table. `UserRole.name` values are stored with the `ROLE_` prefix (e.g. `ROLE_ADMIN`, `ROLE_USER`).
- `AppUser` uses a **UUID v7** primary key (`UuidEntity`, `@UuidGenerator(style = VERSION_7)`; id assigned in-memory at `persist()` — no DB round-trip). Every other entity keeps `Long` IDENTITY (`LongEntity`). FKs to `application_users` (e.g. `user_roles.user_id`) are `uuid`. `V3__migrate_app_user_to_uuid.sql` converts the schema via **drop & recreate** (truncates `application_users`/`user_roles`) — destructive, valid only because there is no production data.
